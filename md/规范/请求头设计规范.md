# 请求头设计规范

本文定义认证请求头、响应头、Token 生命周期和前端对接要求。

## 1. 请求头

| Header | 格式 | 必填 | 说明 |
|---|---|---|---|
| `authorization` | `Bearer <access_token>` | 受保护接口必填 | 后端按小写读取 |
| `Refresh-Token` | `<refresh_token>` | 可选 | 请求头优先，Cookie 兜底 |

前端必须使用：

```http
authorization: Bearer <access_token>
Refresh-Token: <refresh_token>
```

HTTP Header 本身大小写不敏感，但项目约定使用全小写 `authorization`，避免代码和日志口径漂移。

## 2. Refresh Token 双通道

### 2.1 请求头

前端从 `localStorage` 读取 Refresh Token，并显式携带 `Refresh-Token`。

### 2.2 Cookie

登录和刷新成功后，后端同时写：

```text
refresh_token=<token>; HttpOnly; SameSite=...; Path=/; MaxAge=604800
```

HTTP 连接：

```text
SameSite=Lax
```

HTTPS 连接：

```text
Secure; SameSite=None
```

JS 不能读取 httpOnly Cookie。

### 2.3 后端读取顺序

```text
Refresh-Token 请求头
  -> refresh_token Cookie
```

任一通道存在即可尝试刷新。

## 3. 响应头

| Header | 出现时机 | 说明 |
|---|---|---|
| `authorization` | 登录、刷新、改密成功 | `Bearer <access_token>` |
| `Refresh-Token` | 登录、刷新、改密成功 | 新的 Refresh Token 明文 |
| `Set-Cookie` | 登录、刷新、改密成功 | httpOnly Refresh Token |
| `X-Token-Refresh` | 刷新路径 | `ok` / `skipped` / `failed` |
| `X-Auth-Reason` | 401 | `superseded` / `no-session` |

### 3.1 登录成功

```http
authorization: Bearer <access_token>
Refresh-Token: <refresh_token>
Set-Cookie: refresh_token=...
```

### 3.2 刷新成功

```http
X-Token-Refresh: ok
authorization: Bearer <new_access_token>
Refresh-Token: <new_refresh_token>
Set-Cookie: refresh_token=...
```

### 3.3 刷新跳过

同一用户的刷新锁被其它请求占用：

```http
X-Token-Refresh: skipped
```

跳过者不写回旧 Authorization，避免覆盖其它请求刚写的新 Token。

### 3.4 刷新失败

```http
X-Token-Refresh: failed
X-Auth-Reason: no-session
HTTP/1.1 401
```

如果有效版本高于 Token 版本，则：

```http
X-Auth-Reason: superseded
```

## 4. CORS

前端使用 `fetch` 或 axios 时必须允许携带凭据：

```typescript
credentials: 'include'
// 或 axios
withCredentials: true
```

后端必须：

```text
Access-Control-Allow-Credentials: true
Access-Control-Expose-Headers:
  authorization
  Refresh-Token
  X-Token-Refresh
  X-Auth-Reason
```

否则前端无法读取响应头。

## 5. Token 生命周期

| Token | TTL | 说明 |
|---|---|---|
| Access Token | 30 分钟 | JWT，包含 `userId` 和 `version` |
| Refresh Token | 7 天 | 随机字符串，轮转更新 |
| validVersion | 7 天 | Redis 当前有效版本 |
| currentVersion | 8 天 | 新登录版本视图 |

### 5.1 登录

登录会生成新 version：

```text
version = redisIdWorker.nextVersion(userId)
```

旧版本 Token 立即失效。

### 5.2 刷新

刷新不会 bump version：

```text
newVersion = oldVersion
```

### 5.3 修改密码

修改密码会生成全新 Token Pair 并 bump version，使旧 Token 失效。

## 6. Access Token 校验

顺序：

```text
JWT 签名/过期校验
  -> Caffeine 快速版本拒绝
  -> Redis validVersion 最终校验
  -> 判断是否临期
```

临期判断：

```text
剩余时间 > 0
且剩余时间 < 5~10 分钟随机值
```

Access Token 已过期时会解析 Claims，并进入刷新流程。

## 7. Refresh Token 刷新

### 7.1 分布式锁

```text
lock:refresh:{userId}
```

同一用户只有一个刷新任务执行。锁被占用时：

```http
X-Token-Refresh: skipped
```

调用继续放行，由并发刷新请求写回新 Token。

### 7.2 Lua 原子更新

`RefreshExpiredToken.lua` 原子校验并更新：

- Refresh Token；
- Access Token；
- validVersion；
- currentVersion。

### 7.3 422 并发自愈

Refresh Token 不匹配时：

1. `ReadCurrentToken.lua` 读取当前 AT / RT；
2. 仅当 `validVersion == oldVersion` 时返回当前凭证；
3. 版本已变化时拒绝，避免把新登录会话的 Token 交给旧会话。

### 7.4 当前安全限制

当前实现是“并发刷新自愈”，不是完整的 Refresh Token Reuse Detection。

版本不变时，旧 Refresh Token 再次出现可能被当作并发刷新处理。系统当前没有实现“检测到旧 RT 重放后吊销全部会话”的流程。

## 8. 401 处理

### 8.1 no-session

```text
会话不存在
Refresh Token 不存在或过期
JWT 无效
```

### 8.2 superseded

```text
Redis validVersion > Token version
```

表示账号已在其它设备重新登录，当前旧会话应要求重新登录。

## 9. 前端行为

### 9.1 请求发送

1. 从 `localStorage` 读取 Access Token；
2. 只有 JWT 形状合法才发送；
3. 受保护请求携带 `authorization`；
4. 有 Refresh Token 时同时携带 `Refresh-Token`；
5. 原生 SSE 请求也需要 `credentials: 'include'`。

### 9.2 响应更新

每次响应检查：

```typescript
const newAccess = response.headers.get('authorization')
const newRefresh = response.headers.get('refresh-token')
```

Access Token 必须再次验证 JWT 形状后写入，防止坏值 `null` 写入存储。

### 9.3 401

前端处理顺序：

1. 读取 `X-Auth-Reason`；
2. 如果本地 Token 已被其它请求刷新，则用新 Access Token 单飞重试一次；
3. 无法重试时执行一次单飞登出；
4. 清除 AT / RT / 用户信息；
5. `superseded` 与 `no-session` 使用不同提示；
6. 非登录页跳转登录页。

httpOnly Cookie 只能由 `/user/logout` 清除，前端 localStorage 清理不会删除 Cookie。

## 10. 禁止事项

1. 不使用 `Bearer null` / `undefined`。
2. 不把 Refresh Token 只放 localStorage。
3. 不在登录或刷新成功时忽略响应头。
4. 不在 401 时无限重试。
5. 不在前端把 Access Token 写入 Cookie。
6. 不把 Refresh Token 写入日志。
7. 不把已淘汰的 `reuse detection` 方案当作当前实现。
