## 一、总体结论

项目的"乱"不是某一处代码差，而是**每一次迭代都"叠加新实现、从不清理旧实现"**造成的系统性熵增：

| 现象 | 证据 |
|---|---|
| 新旧实现长期并存，靠注释/@Deprecated/开关切换 | 477 行全注释的 `VoucherOrderServiceImpl`、`TaskExecutor`(@Deprecated)、`LegacyPlanRouter`、RedisIdWorker 双实现、`createVoucherOrder`/`saveOrder` 两套下单路径 |
| 同一件事多套写法 | 缓存 4 套（CacheClient/BatchLoadCache/Caffeine 直用/手写 Redis）、Cookie 两处手写、错误语义三套（HTTP 401 / `Result{success:false}` / Lua 数字码） |
| 分层标准不统一 | 有的 Controller 很薄（Blog），有的直操作 Redis 和 Mapper（User/Shop）；Entity 既当请求体又当 VO |
| 测试代码混入生产 | `/test/**` 无鉴权端点、`TokenTestUtil`、`CacheMonitor` 用 `System.out.println` |
| Agent 模块复杂度失控 | 两套规划执行链、4 处工具注册表、15+ 个配置类、单例存请求级状态 |

> 路径约定：下文所有路径均相对于 `picknear/picknear/src/main/java/com/hmdp/`，配置/资源相对于 `picknear/picknear/`。

## 二、🔴 严重：数据一致性与结构性风险（当前环境真实存在）

> 说明：CORS 全开、JWT 测试密钥、`/test/**` 端点、验证码回显这 4 项**不属于本节**——作者确认项目未上公网，这些是有意开启的测试便利设计，详见第三节与第九节"上线前安全清单"。

### S-1. 秒杀链路缺事务一致性与幂等
- **位置**：`service/impl/MqVoucherOrderServiceImpl.java:64-113, 171-243, 335-348`
- **问题**：`saveOrder()` 链路为 Lua 扣 Redis 库存 → DB 落订单 → 发 MQ → 消费者再扣 DB 库存：
  - DB 落单成功但 MQ 发送失败（`:344` 抛异常）→ Redis 已扣、DB 未扣，**两边库存永久不一致**
  - 消费者扣 DB 库存无幂等标记，消息重放会重复扣减
  - "库存不足"是业务终态却走重试 3 次再进死信（`:103-108`），纯浪费
  - `querySeckillVoucher` 里 `AopContext.currentProxy()` 取了代理却**没用**（`:184`，死代码）
- **建议**：订单唯一键（voucherId+userId）DB 唯一索引兜底幂等；DB 落单与 MQ 发送解耦（本地消息表/Outbox 或补偿对账）；消费者扣库存加"已处理"标记；库存不足直接 `basicAck` 不重试。

## 四、🟠 高：架构层面

### H-1. 分层击穿
- **位置**：`controller/ShopController.java:110-114`；`controller/UserController.java:125-137`；`controller/BlogController.java:33-35`；`controller/VoucherController.java:33,41`；`controller/ShopController.java:59-60`
- **问题**：
  - ShopController 直接在 Controller 里 `shopService.query().like(...).page(...)` 拼查询，`shopService` 还是 public 字段
  - UserController 直接拿 `CacheClient` 查 Redis、直接 `userInfoService.getById` 组装 DTO
  - Blog/Voucher/Shop 用 **Entity 直接当请求体**（`Blog` 带 `isLike/icon/name` 等非库字段，前端可注入）；`BlogServiceImpl` 又把 Entity 直接当 VO 返回
- **建议**：查询/缓存逻辑下沉 Service；请求用 `*FormDTO`、返回用 VO，Entity 只在 mapper/service 内部流转。

### H-2. Blog ↔ Follow 循环依赖（@Lazy 掩盖）
- **位置**：`service/impl/BlogServiceImpl.java:50`；`service/impl/FollowServiceImpl.java:42-43`
- **问题**：双向依赖 + 运行期才触发的 @Lazy，是职责划分错误的信号，难以单测、异常难排查。
- **建议**：抽出独立的 Feed 推送服务单向化依赖。

### H-3. 拦截器职责过重 + 分布式锁无所有者标识
- **位置**：`interceptor/RefreshTokenInterceptor.java:40-167, 110-159`；`utils/cache/CacheClient.java:187-202`
- **问题**：一个 preHandle 干了 6 件事（取 token、JWT 校验、Caffeine 用户解析+DB 回填、分布式锁刷新、手写 Set-Cookie、性能告警）。其中锁 `setIfAbsent("1")` + finally `delete` **没有所有者标识**：A 的锁超时被 B 拿到后，A 的 finally 会删掉 B 的锁。`CacheClient.unlock()` 里也留着同样的 TODO（`:199-202`）。
- **建议**：拦截器只做"取 token + 调 AuthService + 写响应"，刷新并发控制/Cookie 下沉 Service；锁释放用 Lua 校验 value（项目里已有 `releaseLockSafely` 的正确范例可复用）。

### H-4. 缓存体系 4 套并存、职责重叠
- **位置**：`utils/cache/CacheClient.java`、`utils/cache/BatchLoadCache.java`、`utils/cache/CacheMonitor.java`、`config/CacheConfig.java`、`service/impl/BlogServiceImpl.java:74-79,154-155,201-202,229-230`
- **问题**：CacheClient（通用单键）/ BatchLoadCache（用户批量预载）/ Caffeine 直用 / 各处手写 Redis 并存；"用户信息"在 Caffeine、`cache:userinfo:`、`login:userinfo:`（AuthServiceImpl 注释承认已废弃）三处出现；Blog 侧四个方法重复"JSON 序列化+随机过期+写缓存"。新增缓存时不知道该用哪个。
- **建议**：收敛为统一 CacheService 抽象；明确"用户信息"只走 BatchLoadCache，CacheClient 只保留通用单键流程。

### H-5. 事务边界混乱
- **位置**：`service/impl/MqVoucherOrderServiceImpl.java:195-206`；`service/impl/BlogServiceImpl.java:208`；`service/impl/VoucherServiceImpl.java:39`
- **问题**：事务里发了 MQ（外部副作用）、写了 Redis、推了 Feed。Redis 写失败时 DB 回滚但 Redis 已写，一致性被破坏。
- **建议**：事务只包 DB 写；MQ 发送/Redis 写/Feed 推送移到事务提交后（`TransactionSynchronization` afterCommit 或 Outbox）。

### H-6. 错误语义三套并存、无统一错误码
- **位置**：`exception/WebExceptionAdvice.java` 全文；`dto/Result.java`；`interceptor/LoginInterceptor.java:28`、`interceptor/RefreshTokenInterceptor.java:82,96,123`；`service/impl/AuthServiceImpl.java:208-242`；`enums/TokenRefreshCode.java`（import 了未使用）
- **问题**：拦截器直接 401（不走 Result）；业务失败返回 HTTP 200 + `Result{success:false}`；AuthServiceImpl 用 Lua 数字码 200/422/413/421/431。`Result` 无 `code` 字段，前端只能靠字符串文案判断错误类型；`WebExceptionAdvice` 只有 3 个 handler，登录失败直接回显 `e.getMessage()`（信息泄露）而服务器异常却吞掉具体信息。
- **建议**：`Result` 加业务 `code` + 错误码枚举；拦截器鉴权失败也走统一返回；新增兜底 handler；敏感信息只进日志不回传。

## 五、🟡 中：Agent 模块复杂度与重复

### M-1. 两条并行的"规划→执行"链（agent 最核心的乱源）
- **位置**：`agent/task/TaskPlanner.java`、`agent/plan/TreePlanRouter.java`、`agent/plan/LegacyPlanRouter.java`、`agent/plan/PlanRouter.java`、`agent/routing/TreeCatalogBuilder.java`、`agent/routing/CompactCatalogBuilder.java`、`agent/routing/CatalogBuilder.java`、`agent/routing/ToolRouter.java`、`agent/task/TaskExecutor.java`（@Deprecated）、`agent/task/TaskQueue.java`
- **问题**：
  - 默认链：`TreePlanRouter → TreeCatalogBuilder → ToolIntentTree → SubTaskAgent → Serial/BatchToolLoop`
  - Legacy 链（默认休眠，靠 `feature.tool-routing.enabled` 开关）：`LegacyPlanRouter → ToolRouter/CompactCatalogBuilder → TaskExecutor/TaskQueue`
  - `TaskExecutor`/`TaskQueue` 标了 @Deprecated 却不删；`CatalogBuilder` 是没有任何多态调用方的死抽象。维护者要同时理解两套体系才能改代码。
- **建议**：删 legacy 链（`LegacyPlanRouter`/`TaskExecutor`/`TaskQueue`/`CatalogBuilder` 及配套），保留单一 Tree 链。

### M-2. 工具注册信息 4 处硬编码、各自漂移
- **位置**：`agent/routing/CompactCatalogBuilder.java`（TRIGGER_KEYWORDS）、`agent/routing/ToolIntentTree.java`（NODES）、`agent/prompt/seed/PromptSeeder.java`（TOOL_NAMES）、`agent/prompt/PromptKeys.java`（tool()）
- **问题**：新增一个工具要同步改 4 处，漏一处就是线上 bug。
- **建议**：从 `@Tool` 注解/工具定义 Provider 单一来源生成目录/意图树/提示词。

### M-3. 单例 Bean 存请求级上下文
- **位置**：`agent/tool/ToolBeanCollector.java:62,172`；`agent/service/impl/AiServiceImpl.java:89,154`
- **问题**：`volatile String conversationId` 是**实例字段**，每个请求 `setConversationId()`，高并发多用户对话时互相覆盖（GuardedToolCallback 实际从 ToolContext 读，该字段的写入是"看似在传、实际无效"的迷惑设计）。这是 ThreadLocal 语义误用的典型。
- **建议**：请求级数据一律经 ToolContext/ChatContext 显式传递，删除单例上的可变会话字段。

### M-4. 工具直钻数据访问层
- **位置**：`agent/tool/impl/BlogQueryTool.java`、`ShopQueryTool.java`、`VoucherQueryTool.java`、`UserQueryTool.java`
- **问题**：直接用 `service.query().eq().page()` 裸查 MyBatis-Plus，绕过了封装好的缓存/业务方法——Agent 工具与业务 Service 层没有对齐。
- **建议**：工具只调 Service 暴露的业务方法。

### M-5. 上帝类 + 补丁式复杂度
- **位置**：`agent/task/TaskPlanner.java`（518 行、14 个 @Resource）、`agent/service/impl/AiServiceImpl.java:150-289`、`agent/controller/ChatController.java`、`agent/observability/support/*`、`agent/config/ChatModelObservationConventionConfig.java`
- **问题**：`doChatWithToolcall` 手动管 Observation scope、重试循环、SSE 逐 token、全局 mark/clear 标记。SSE 那套"根 span resume / 兜底 TTL / 三回调只留日志"的复杂设计，根因是 **ThreadLocal 上下文进不了异步线程**（`UserHolder` 只有 ThreadLocal），于是用 `TaskSnapshot`/`ChatContext`/`ToolContext` 到处手递 userId——结构性缺陷的补丁堆叠。
- **建议**：异步链路显式传参规范化（或引入上下文传递包装），拆解上帝类。

### M-6. 其他
- **位置**：`agent/guard/*`（5 个 policy + Vote + `ConfirmRequiredException` 异常流）、`agent/aspect/ToolPermissionAspect.java`、`agent/config/`（15+ 配置类）
- **问题**：Guard 投票机制对当前规模过度设计；`ToolPermissionAspect` 用"错误字符串当工具结果"与异常流失败语义不一致；配置类散落（`PromptGuardProperties`/`TraceProperties`/`SubTaskProperties`/`PromptProperties`/`FeatureProperties`…），yaml 里 5 组自定义配置 + 魔法开关。
