# 后端架构拆分方案（设计模式对齐版）

> **版本**: v1.0
> **日期**: 2026-08
> **目标**: 以 `agent` 模块已验证的设计模式为标杆（策略投票 / 责任链 / 工厂 / 单一来源注册表），对 `com.hmdp` 业务代码做职责拆分与模式化收敛。
> **前置阅读**: [后端架构审查报告](./后端架构审查报告.md)（问题清单与已整改项）、[Agent模块架构设计](../agent/Agent模块架构设计.md)（模式参考）。
> **状态**: ⚪ 方案待评审 — 本方案**只规划、不动代码**，评审通过后按 Phase 实施。

---

## 一、为什么拆分：现状病灶

| # | 病灶 | 证据（当前代码） | 后果 |
|---|------|------------------|------|
| 1 | **上帝类** | `BlogServiceImpl` 374 行（查询/点赞/Feed 推送/图片/收藏 6 职责）；`AuthServiceImpl` 369 行 12 个 `@Resource`；`MqVoucherOrderServiceImpl` 349 行（**MQ 消费者 + 订单创建 + Lua 扣减 + MQ 发送** 混一炉）；`GuardedToolCallback` 340 行；`UserServiceImpl` 321 行（密码登录/验证码登录/创建用户/改密/验证码） | 改一处牵全身、单测难写、新人无法理解 |
| 2 | **分层击穿** | `UserController` 直接注入 `CacheClient` 查 Redis（`:125-137`）；`ShopController` 直接拼 `query().like().page()`（`:110-114`）；`BlogQueryTool` 等 agent 工具直钻 Mapper 裸查 | Controller 承载业务、缓存细节泄漏到 Web 层 |
| 3 | **事务/一致性边界错** | `createVoucherOrder` 事务内 `convertAndSend` 发 MQ（`:205`）；`saveOrder` Lua 扣 Redis → DB 落单 → 发 MQ 无兜底，MQ 失败即 Redis/DB 不一致 | 秒杀链路数据一致性风险（审查 S-1） |
| 4 | **Controller 过厚** | `UserController` 267 行：登录流程、Cookie 写入、头像文件校验/上传、图片类型白名单全在 Controller | 无法复用、无法单测 |
| 5 | **缓存 4 套并存** | `CacheClient` / `BatchLoadCache` / Caffeine 直用 / 手写 Redis（审查 H-4） | 新增缓存不知用哪套 |
| 6 | **循环依赖** | `BlogServiceImpl ↔ FollowServiceImpl`（@Lazy 掩盖，审查 H-2） | 职责划分错误的信号 |
| 7 | **包结构扁平** | `com.hmdp` 下 controller/service/… 全平铺；`entity` 包混入 `SnowflakeIdQueue`/`TokenVersionCache`/`UserinfoCache` 非 DB 对象 | 无域边界，自动化基建（如模块扫描）无从下手 |
| 8 | **Agent 遗留双链** | `agent/legacy/*`（TaskExecutor/TaskQueue/LegacyPlanRouter）与 Tree 链并存 | 维护者需同时理解两套体系 |

> 对照组：`agent` 模块同类问题处理得干净——大业务拆子域（`PlanLoopExecutor → SubAgentRoundExecutor/FallbackRoundExecutor`）、扩展点用策略（`ToolGuardPolicy` 投票）、多实现用工厂（`PermissionValidatorFactory`）、注册信息单一来源（`@ToolMeta + ToolRegistry`）。**本次拆分就是把 agent 已验证的这套"模式方言"推广到全部业务域。**

## 二、目标架构

### 2.1 顶层包结构（物理重组，Phase 0）

```
com.hmdp
├── PickNearApplication
├── common/                  # 跨域通用：错误码/异常/上下文/幂等/工具
│   ├── exception/           #   BizException、WebExceptionAdvice
│   ├── result/              #   Result、ErrorCode
│   ├── context/             #   UserHolder（请求级上下文，后续可服务化）
│   ├── idempotent/          #   @Idempotent 注解 + 切面（新增）
│   ├── lock/                #   LockTemplate（分布式锁统一封装，替代散落 setIfAbsent）
│   └── util/
├── config/                  # Spring 配置（保留现状，逐步收敛）
├── auth/                    # 认证域（拆分自 AuthServiceImpl + UserController 登录部）
│   ├── controller/  service/  dto/
│   ├── token/               #   TokenService（JWT 生成/校验/刷新）
│   ├── session/             #   SessionContextService（用户上下文注入/登出）
│   ├── verifycode/          #   VerifyCodeService（验证码发送/消费）
│   └── login/               #   LoginStrategy 策略族（见 3.1）
├── user/                    # 用户域：资料/头像/签到
│   ├── controller/  service/  dto/
│   ├── profile/             #   资料查询/更新、头像上传
│   └── sign/                #   ISignService（已独立，归位）
├── shop/                    # 商铺域：Shop / ShopType
├── voucher/                 # 优惠券秒杀域（拆分自 MqVoucherOrderServiceImpl）
│   ├── controller/  service/  dto/
│   ├── stock/               #   SeckillStockService（Lua 原子扣减/回补）
│   ├── order/               #   VoucherOrderService（DB 落单/查询）
│   ├── mq/                  #   VoucherOrderProducer / VoucherOrderConsumer
│   └── idempotency/         #   订单唯一键幂等
├── content/                 # 内容社交域（原 blog + follow 合并，解除循环依赖）
│   ├── blog/                #   BlogQueryService、BlogLikeService、BlogImageService
│   ├── feed/                #   FeedPushService（独立，单向依赖 follow）
│   └── follow/              #   FollowService（只留关注关系）
└── agent/                   # AI 域（保持现状，仅收敛 legacy，见 3.6）
```

### 2.2 分层纪律（每个域内统一）

```
Controller（薄：参数解析 + DTO 装配 + 调 Service）
   ↓
Service（编排：事务边界、调用策略族/执行器）         ← 唯一允许 @Transactional 的层
   ↓
策略/执行器（无状态单一职责，可插拔）                ← 对齐 agent guard 风格
   ↓
基础设施（cache / mq / redis / oss，一律经接口）
```

**硬性规则**：
1. Controller 禁止注入 `StringRedisTemplate` / `CacheClient` / Mapper / 拼 `query()`。
2. `@Transactional` 只出现在 Service 编排方法；事务内禁止发 MQ / 写 Redis 外部副作用（改 afterCommit 或 Outbox）。
3. Entity 只在 mapper/service 内部流转；对外一律 DTO/VO。
4. 新增扩展点优先"接口 + 策略收集（注入 `List<XxxStrategy>`）"，对齐 `ToolGuardManager`。

## 三、设计模式落点（每域 = 一个模式样板）

### 3.1 认证域：策略模式拆分登录（对齐 guard 投票思想）

**现状**：`UserServiceImpl.login()` 里 `if (form.hasPassword) loginByPassword else loginByCode` 分支 + `AuthServiceImpl` 12 依赖的"家政妇"式职责。

**改造**：
```
LoginStrategy (接口)
├── PasswordLoginStrategy   # 密码 + BCrypt + 账户锁定
├── CodeLoginStrategy       # 验证码 + 消费
└── LoginStrategyRegistry   # Map<LoginType, LoginStrategy>（仿 PermissionValidatorFactory）

UserService.login() → registry.get(loginForm.type()).login(loginForm)
```

**顺带拆分 AuthServiceImpl**（369 行 → 3 个小类）：
- `TokenService`：JWT 生成/校验/刷新 Lua 编排（保留 5 个 RedisScript，全部内聚）；
- `SessionContextService`：`saveUserToContext` / `revokeTokens`（用户上下文、登出）；
- `VerifyCodeService`：`consumeVerifyCode` + 发送（与 `UserServiceImpl.sendCode` 合并收敛）。

**收益**：新增登录方式（如 OAuth2）零改动加一个策略类；Token/验证码/上下文各自可单测。

### 3.2 秒杀域：拆分"四合一" + 模板方法收敛 MQ 消费

**现状**：`MqVoucherOrderServiceImpl` 一个类同时是 Service、Lua 执行器、MQ Producer、MQ Consumer——四个生命周期耦合，且事务内发 MQ、消费无幂等。

**改造**：
```
SeckillStockService        # Lua 原子扣减 + 回补（querySeckillVoucher 的 Lua 部分）
VoucherOrderService        # DB 落单/唯一键幂等（voucherId+userId 唯一索引）
VoucherOrderProducer       # 事务提交后发 MQ（afterCommit，修复事务内发 MQ）
VoucherOrderConsumer       # 消费：扣 DB 库存 + 幂等标记（消费模板见下）

AbstractMqConsumer<T>      # 模板方法：重试计数/deadLetter/ack 封装
└── VoucherOrderConsumer extends 之，只写业务逻辑
```

**要点**：`rejectAndRequeueWithIncrement` 那 40 行手写重试 → 模板方法统一（后续所有 listener 复用）；"库存不足是业务终态"不再瞎重试 3 次。

### 3.3 内容域：拆分上帝类 + 解除循环依赖

**现状**：`BlogServiceImpl` 374 行六职责；`Blog ↔ Follow` @Lazy 循环。

**改造**：
```
BlogQueryService     # queryById/queryHot/queryUserList/queryByUserId/queryMyBlog
BlogLikeService      # likeBlog/isLiked（Redis Set + 定时同步 DB）
BlogImageService     # saveBlog/updateBlogImages（上传 + 落 DB）
FeedPushService      # 新依赖方向：Feed → Follow（单向），BlogService 不再注入 followService
FollowService        # 只保留关注/取关/关注列表
```

**依赖方向修正**：`BlogServiceImpl` 删除 `@Lazy IFollowService`，改由 `FeedPushService` 注入 Follow Mapper 做粉丝查询。循环依赖拆平。

### 3.4 横切：缓存/锁/幂等收敛（门面 + 模板方法）

**缓存**（收敛审查 H-4 的 4 套）：
```
CacheStrategy (接口)           # get/set/evict，带过期与防穿透参数
├── RedisCacheStrategy
├── CaffeineCacheStrategy      # 本地优先
└── CacheManager (门面)        # 按 key 前缀路由到策略；内部统一 JSON 序列化/随机过期/空值兜底
```
存量 `CacheClient`/`BatchLoadCache` 演进为 `CacheManager` 的两种策略实现，调用方统一经 `CacheManager`。

**锁**（修复审查 H-3 锁无所有者标识）：
```
LockTemplate          # tryLock(key, timeout) → AutoCloseable；释放用 Lua 校验 value
```
替换 `RefreshTokenInterceptor`/`AuthServiceImpl.refreshTokenPairWithLock` 里的 `setIfAbsent("1")+delete` 手写锁（已有正确范例 `releaseLockSafely` 可复用）。

**幂等**（秒杀/下单通用）：
```
@Idempotent(key = "#orderId") + IdempotentAspect   # Redis SETNX + 完成标记
```

### 3.5 Controller 瘦身

- `UserController`：登录/Cookie/文件校验/头像全部下沉——登录走 `auth` 域，头像走 `user/profile` 的 `ProfileService`（`ALLOWED_ICON_TYPES`/`MAX_ICON_SIZE` 常量进配置或 Profile 域常量）。
- `ShopController`：`query().like()` 拼查询 → `ShopQueryService.queryByName()`。
- 工具层 `BlogQueryTool` 等：改调 `BlogQueryService` 业务方法，禁止裸 Mapper（对齐审查 M-4）。

### 3.6 Agent 域收敛（与本次拆分同步）

- 删除/归档 `agent/legacy/*`（`TaskExecutor`/`TaskQueue`/`LegacyPlanRouter`/`CatalogBuilder` 死抽象），保留单一 Tree 链。
- guard 模式保持不动（它就是标杆）；`GuardedToolCallback` 340 行按需拆回调/决策/执行三小步（可选，低优先）。

## 五、明确不做 / 边界

1. **不改对外 HTTP API**（路径/参数/响应结构与 `md/ops/前端开发文档.md` 保持一致）——只拆内部结构。
2. **不引入新框架**（不建多模块 Maven、不引 DDD 基建）：当前单模块 + 分层规则足够，拆分以"类与包"为粒度。
3. **测试便利设计**（T-1~T-4：CORS/JWT 密钥/`/test/**`/验证码回显）不在本次范围，保留至上线条目。
4. **守卫与 Hook 链**为 agent 标杆，不做返工，仅作为其他域的模式模板。

### 7.4 迁移工程化操作规程（每域适用）

> ⚠️ **硬性要求：文件移动一律使用 `git mv`**（禁止 IDE/资源管理器普通移动）。原因：普通移动在 git 视角是"删除旧文件 + 新增同内容文件"，`git blame`/`git log`/code review 全部丢失历史追踪；`git mv` 让 git 以 rename 识别（`R` 状态），后续 review 能看到 `{旧包} => {新包}` 的纯移动 diff。P0 shop 试点已验证：10 文件全部 `RM`、diff 0 行变更 ✅。

```
① git mv 整域文件（保留 rename 轨迹；可用 git mv 批量：git mv dir old new）
② 改 package 声明（逐文件）
③ 编译 → 按报错清理残留 import（或 grep 旧全限定名）
④ 更新 @MapperScan（新增 <域>.mapper）与 type-aliases-package（prod yaml）
⑤ 同步 src/test 同级迁移（测试类包名须与生产类一致，同样 git mv）
⑥ 编译 + 跑该域相关单测 + 全量测试
⑦ 提交（遵循 git 规范）+ 回填本方案与审查报告跟踪表
```

**提交前验证 rename 完好**：
```
git add -A && git diff --cached --stat -M    # 期望：{...} => {...} 模式，且变更行数为 0（纯移动）
git status --short                            # 期望：R（而非 D + ?? ）
```

**提交规范落点**（遵循 `md/规范/git规范.md`，本重构场景映射）：

- 所有 Phase 统一用 `refactor` 类型（不改变外部行为——对外 HTTP API 不变，符合 refactor 定义；`chore` 只留给构建/依赖类改动如 surefire 配置）。
- scope 规范表无"包重组/域拆分"直接对应项，按"可自定义但必须简短"取：

| Phase | 建议提交 Header 示例 |
|-------|----------------------|
| P0 包迁移（每域一个提交） | `refactor(package): shop 域迁移至 com.hmdp.shop.*`、`refactor(package): auth 域迁移拆分`… |
| P1 秒杀域 | `refactor(voucher): 秒杀四合一拆分与 MQ 消费模板化` |
| P2 认证域 | `refactor(auth): LoginStrategy 策略族拆分登录` |
| P3 内容域 | `refactor(blog): Blog 拆分与 Feed 依赖单向化` |
| P4 横切 | `refactor(cache): 缓存收敛为 CacheManager 门面`、`refactor(security): LockTemplate 统一分布式锁` |
| P5 agent 收敛 | `refactor(agent): 收敛 legacy 双链` |

- Header：`subject` 中文 ≤ 50 字，`type`/`scope` 英文，冒号后一个空格，结尾无句号。
- Body：分点 `- ` 列出 What（代码层面变动）+ 一段 Why（业务背景/技术决策），每行 ≤ 72 字符，禁贴大段代码。

**避坑清单**：
- `@MapperScan` 少一个包 = 运行时 `NoSuchBeanDefinitionException`（编译期发现不了）。
- `type-aliases-package` 只配 `com.hmdp.entity` 时，XML `resultType`/`parameterType` 简写别名失效（当前仅 UserMapper.xml/VoucherMapper.xml，迁移用户域时最易踩）。
- ⚠️ **有自定义 SQL 的 Mapper 迁移时必须同步 XML**：`VoucherMapper.xml` 的 `namespace` 与 `resultType` 全限定名都要改成新包，否则运行期 `Statement not found`（编译期发现不了）。迁移前先 glob `resources/mapper/*.xml` 盘点哪些 entity/mapper 有 XML。
- hutool `JSONUtil.toBean` 按全类名反射，不受包移动影响；但要留意序列化字段与 `@JsonProperty` 依赖。

- ⚠️ **本机 `mvn test` 的 MockMaker 环境坑**（P0 实测）：JDK 17/21 默认拒绝动态 agent 加载，Mockito inline mock maker 报 `Could not initialize plugin: MockMaker`。已在 pom 的 surefire `<argLine>` 固化 `-XX:+EnableDynamicAgentLoading -Djdk.attach.allowAttachSelf=true`（两参数缺一不可：JDK 17 需后者，JDK 21 需前者）。注意：**pom 显式声明 argLine 后，命令行 `-DargLine=...` 会被其覆盖**，CI 若要传参需改 pom 或 profile。
- ⚠️ **`picknear/.gitignore` 第 36 行 `/src/test/` 忽略了整个测试目录**（项目既有状态，测试文件从未进版本库）。因此测试侧 import 同步仅影响本地工作区，不会进入提交；`mvn test` 验证请基于工作区执行（与提交内容一致即可）。如后续希望测试入库，需单独评估移除该 ignore（超出本方案范围，建议项目统一决策）。

- ⚠️ **本机 `target/` 目录常被 IDE/进程锁定不可写**，`mvn compile/test` 建议用独立输出目录（`-Dmaven.build.directory=<temp>`）或在 IDE 侧执行，避免"拒绝访问"误判为代码问题。

### 11.2 目标组件设计

#### 11.2.1 `LockTemplate`（`common/lock`，门面 + 模板方法）

```
LockTemplate.tryLock(key, ttl) → LockHandle(AutoCloseable)
  - value = UUID 随机串（所有者标识）
  - SET key value NX EX ttl
  - close()/unlock() 执行 Lua：if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end
LockTemplate.withLock(key, ttl, Supplier<T>)  # 便捷模板：try-with-resources 包裹
```

- **替换 4 处手写锁**（AuthServiceImpl/BlogServiceImpl/FollowServiceImpl/CacheClient），锁语义（key/ttl/降级行为）保持。
- `FollowServiceImpl.queryFollowStatus` 的"抢锁失败 sleep 50ms 重试 3 次"模式：保留在业务侧（循环调 `tryLock`），LockTemplate 不内嵌重试（保持无状态简单）。
- 新代码禁止再出现 `setIfAbsent + delete` 对（验收 grep）。

#### 11.2.2 `CacheManager`（`common/cache`，门面）

收敛**通用单键缓存**（String 结构）为唯一入口：

```
CacheManager.queryWithCache(keyPrefix, id, clazz, loader, ttl)   # 穿透防护 + 逻辑过期 + 随机 TTL 内聚
CacheManager.set(key, value, ttl)
CacheManager.setWithLogicalExpire / setWithBlankExpire
CacheManager.evict(keyPrefix, id)
```

- `CacheClient` 的 5 个公开方法 + 私有重建逻辑整体迁入 CacheManager 内部实现，**CacheClient 删除**。
- 内部线程池改 **Spring 托管有界池**（复用 `SchedulingThreadConfig` 或独立 `cacheRebuildExecutor` bean，替代静态 `Executors.newFixedThreadPool(10)`）。
- **BatchLoadCache 不并入**（数据形态不同：Hash 批量 vs String 单键），保留为"用户信息批量通道"专用组件，职责写入类注释。

#### 11.2.3 `@Idempotent`（`common/idempotent`，AOP）

```
@Idempotent(key = "#orderId", ttl = 10)   # SpEL 表达式取业务键
IdempotentAspect：Redis SETNX idem:{key} + TTL
  - 首次请求：执行并标记完成（可选"执行中/已完成"双状态）
  - 重复请求：直接返回成功（防重放）
```

- 落点建议（按需使用，不强行全上）：`VoucherOrderController.saveOrder`（秒杀外层防重，Redis Lua 已有内层重复判断，两者互补）、`BlogPublishService.saveBlog`（防双击重复发布）、`FollowService.follow`（防抖）。
