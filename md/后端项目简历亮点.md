## 项目概述

基于开源点评项目二次开发，重点优化**用户认证安全**与**高并发库存扣减**逻辑。云服务器 Docker 部署 Redis 和 RabbitMQ，本地运行 Spring Boot 应用 + MySQL，使用 JMeter 和 wrk 做压力测试。

**技术栈**：Spring Boot + MySQL + Redis + Lua + RabbitMQ + Caffeine + MyBatis-Plus + Spring AI（LLM Agent）+ Langfuse（AI 观测）

**部署架构**：云服务器（Docker: Redis + RabbitMQ）← 本地应用（Spring Boot + MySQL）← Nginx 反向代理 ← 前端 Vue

## 一、认证与安全模块（Auth / Security）

**一句话**：针对单 Token 重放攻击与并发刷新乱序问题，设计双令牌 + 版本号校验体系，联合 Redis Lua 保障刷新原子性。

**双 Token 机制**：
- Access Token（JWT，30 分钟，含 userId + version）
- Refresh Token（UUID，7 天，HttpOnly Cookie 防 XSS 窃取）
- Access Token 暴露于请求头、有效期短；Refresh Token 藏于 Cookie、有效期长——攻击者盗取 Access Token 也只能在 30 分钟内使用

**两级版本校验（Caffeine + Redis）**：
- JWT claims 内嵌 `version`，Redis 存当前最新版本号
- Caffeine `tokenValidVersionCache` 做快速拒绝——版本不匹配在内存层直接拦截，不查 Redis
- Redis 做最终版本兜底校验
- 改密码 / 重新登录 → bump version → 旧 Token 即使 JWT 签名正确也被拒
- 结果：**Token 主动失效成功率 100%**

**刷新原子性**：
- 登录时 `REDIS_LOGIN_SET_TOKEN` Lua 脚本原子写入 Token + Refresh + Version，不先 DEL 再 SET（避免主从切换丢 key）
- 临期/过期刷新统一走 `RefreshExpiredToken.lua` **Lua 原子刷新**（newVersion=oldVersion 不 bump，版本一致性由 Lua 守卫保证；返回码 200/413/421/422/431 区分成功/被顶替/无会话/RT 不匹配）
- 422 并发容错：`ReadCurrentToken.lua` 原子读取当前凭证，**内含版本守卫**（validVersion==oldVersion 才返回），不会把新登录凭证泄露给旧会话
- 401 透传 `X-Auth-Reason: superseded | no-session`，前端区分"账号在别处登录"与"登录过期"，并发 401 单飞处理
- 验证码原子消费：`ConsumeVerifyCode.lua` GET+DEL 一条命令，防止验证码重复使用

**密码安全**：
- `PasswordEncoder` 用 BCrypt 加密，兼容旧 MD5+盐格式
- 登录成功时自动升级旧密码为 BCrypt
- 防暴力破解：Redis INCR 计数 24h 窗口，连续 10 次错误锁定 30 分钟

**类名**：`RefreshTokenInterceptor`、`LoginInterceptor`、`AuthServiceImpl`、`JwtUtil`、`PasswordEncoder`、`REDIS_LOGIN_SET_TOKEN`（Lua）、`ConsumeVerifyCode.lua`、`tokenValidVersionCache`（Caffeine Bean）

## 二、缓存与拦截器优化（Cache / Interceptor）

**一句话**：拦截器强依赖 Redis 同步查询导致响应延迟，引入 Caffeine 本地缓存配合异步批量回填策略，拦截器平均耗时缩短 50ms。

**问题**：每个请求的拦截器都要查 Redis 校验 Token 版本和用户信息，Redis 同步查询带来固定延迟，拖累整体 TPS。

**解法——两级缓存 + 异步批量回填**：

| 缓存 | 内容 | 策略 |
|------|------|------|
| Caffeine L1 | Token 版本号（`tokenValidVersionCache`） | 写入后 5 分钟过期，过期后触发 CacheLoader 返回默认值 |
| Caffeine L2 | 用户信息（`userinfoCache`） | 20 分钟过期、10 分钟异步刷新，刷新期间返回旧值不阻塞 |
| Redis L2 | 店铺/博客/用户信息 Hash | 多级回退，Pipeline 批量读写 |
| MySQL L3 | 全量持久化 | 兜底查询 |

**BatchLoadCache 定时批量加载**：
- `@Scheduled(fixedRate = 2000)` 每 2 秒取一批待加载的 userId
- Pipeline 批量查 Redis Hash → 未命中再批量查 DB → Pipeline 批量写回 Redis
- 双 Set（`usingUserIds` + `writingUserIds`）避免并发读写冲突
- 修改用户资料时同步刷新 Caffeine，保证一致性

**缓存三防（击穿 / 穿透 / 雪崩）**：
- **击穿**：`CacheClient.queryWithLogicExpire` 逻辑过期——未过期直接返回，已过期**立即返回旧数据** + 后台线程异步重建，物理缺失抢锁提交重建、没抢到返回 null 降级
- **穿透**：DB 查不到时写入空值占位符 `""`，短 TTL（有效 1h / 无效 5min）
- **雪崩**：TTL 全部加随机偏移（博客 30+[0,30]min 随机）

**类名**：`RefreshTokenInterceptor`、`CacheClient`、`BatchLoadCache`、`CaffeineConstants`、`CacheConfig`

**量化成果**：
- 拦截器平均耗时 **缩短约 50ms**
- 空接口 TPS：**2800 → 5500**
- wrk 压测峰值 **突破 16000 QPS**

## 三、秒杀模块（Seckill）

**一句话**：高并发下单瞬间数据库连接池被打满且易引发超卖，采用 Redis 预减库存 + RabbitMQ 异步削峰架构，Lua 脚本原子执行库存校验与一人一单拦截。

**秒杀流程**：

```
请求 → MqSeckill.lua（Redis 原子校验） → 返回订单 ID  → RabbitMQ 异步消费 → 真正扣 MySQL 库存
```

**Lua 脚本（`MqSeckill.lua`）原子操作**：
1. 校验库存存在（EXISTS）
2. 校验用户未下单（SISMEMBER）
3. 预扣库存（DECR → 若 < 0 则回滚）
4. 记录用户（SADD）
5. 存储订单摘要（HMSET + 24h 过期）
6. 返回状态码（200/501/502/511）

**RabbitMQ 异步削峰**：
- Lua 通过后直接返回订单 ID，MySQL 落库交给 MQ 异步消费
- 消费时再用 `stock > 0` 乐观锁兜底
- 消费失败 → `x-retry-count` 消息头自增重试，最多 3 次 → 超限进死信队列

**订单号生成优化**：
- 原方案：实时 INCR Redis 生成，占用核心链路
- **改**：`RedisIdWorker` + `SnowflakeIdQueue` 本地预生成队列
- 启动时批量预取 10000 个 ID，消费完触发下一批
- **单笔请求固有耗时降低 50ms**

**类名**：`MqVoucherOrderServiceImpl`、`seckillScript`（MqSeckill.lua）、`RedisIdWorker`、`SnowflakeIdQueue`、`SeckillOrderCode`

**量化成果**：
- 数据库瞬时查询量 **下降 90%**
- 压测验证 **零超卖**
- 扣库存瓶颈从 MySQL 行锁移到 Redis 单线程

## 四、社交模块（Feed / Follow / Like）

**一句话**：推模式 Feed 流 + 懒回填；Redis Set+ZSet 分布式点赞；Set 交集查共同关注。

### Feed 流 — 推模式 + Pipeline 批量
- **发布推送**：`updateBlogImages` → `pushBloToFansBatch`，Redis Pipeline 批量写入粉丝 Feed ZSet
- **Feed 查询**：`queryBlogOfFollow` 用 `reverseRangeByScoreWithScores` 降序滚动分页
- **懒回填**：首次查询 Feed 时 ZSet 为空 → 遍历关注列表，每个被关注者回填最近 20 篇
- **关注回填**：新关注时立即回填历史博客（最近 20 篇）

### 分布式点赞 — Set + ZSet + 分布式锁
| 结构 | 用途 |
|------|------|
| Set `user:liked:{userId}` | 存用户点赞过的博客 ID，保证一人一赞 |
| ZSet `blog:liked:{blogId}` | 存点赞用户 + 时间戳，取前 5 名展示"谁赞了我" |
| 分布式锁 3s 过期 | 防并发点赞/取消 |

### 关注/共同关注
- 双向 Set 维护关注列表 + 粉丝列表
- `opsForSet().intersect()` 共同关注交集
- 关注状态查询：多级缓存 + 分布式锁 + 空值防穿透，最多重试 3 次

**类名**：`BlogServiceImpl`、`FollowServiceImpl`、`ScrollResult`

## 六、AI Agent 模块（详见《Agent 模块简历亮点》）

**一句话**：Spring AI + DashScope 智能对话，两道安全闸口防越权，两阶段规划 + 真流式 + 全链路可观测 + 业务历史会话 + token/延迟成本治理（工具路由 + 上下文压缩），具备生产级可用性。

| 能力 | 机制 |
|------|------|
| 两道安全闸口 | 前置 `PromptHookChain` 注入检测（本地规则 + Redis 限流，异常降级）；执行 `GuardedToolCallback` 过 4 个 Policy + `@RequiredDataPermission` AOP 数据归属 |
| 两阶段规划 | TaskPlanner 决策 → 分解 → 子任务异步执行 → LLM 合并最终答案；三层校验防非法工具调用 |
| 真流式 | 直连 `DashScopeChatModel.stream()` 逐 token 推送 + `ObservedSseEmitter`；SSE meta/progress/error 推阶段进度 |
| 全链路观测 | AgentTracer/AgentSpan + Langfuse OTLP，session→subagent→tool_call→guard 全链路同 traceId；观测白名单防配额耗尽 |
| 业务历史会话 | `agent_conversation`/`agent_message` 表，会话列表 + 续聊；PLANNING 回合落最终答案，best-effort 不阻塞主链路 |
| 自动注册 | `@TargetTool` 注解 + `ToolBeanCollector` 启动扫描、批量注册、包装 Guard |
| 成本治理 | 紧凑目录 + 一体化 LLM 路由（`__UNCERTAIN__` 保底重跑）；手动工具循环 + LLM 结果压缩，原始结果不进上下文 | 规划按需加载工具提示词；子 agent 上下文累积 O(1) 不随轮次涨（预计累计输入 ~57% 削减） |

**结果**：上线至今未发生越权操作；一次"长沙天气"规划流程 9 层 span 全链路可追溯；加新工具只需加注解，安全不依赖人肉记忆；子 agent 上下文从逐轮翻倍（1k→3k→5k）改为 O(1) 累积。

1. `RefreshExpiredToken.lua` 刷新为什么不 bump version？安全性上有什么取舍？
