## 1. 背景与问题

基于 langfuse 抓取调用 agent 的耗时记录（格式化调用树，`chat` 行右侧 `N → M (∑ K)` 为 输入token → 输出token (总计)）。优化前的观测树中，`agent.subagent` 下 3 次 `subagent-chat` 的输入 token 逐轮翻倍：

```
agent.round.1                                            11.39s
└─ agent.subagent                                     8.19s  (7 items)
   ├─ subagent-chat qwen-plus-2025-07-28              0.87s  [1,001 → 17 (∑ 1,018)]
   ├─ tool_call query-published-blogs                 0.22s
   ├─ subagent-chat qwen-plus-2025-07-28              0.66s  [3,045 → 36 (∑ 3,081)]
   ├─ tool_call query-weather                         0.01s
   └─ subagent-chat qwen-plus-2025-07-28              6.12s  [5,131 → 425 (∑ 5,556)]
```

同一轮内子 Agent 三次调用输入 token `1,001 → 3,045 → 5,131`，最后一次 5,131 输入只换 425 输出（输入/输出比约 12:1）。**每次调用的上下文都在膨胀，且每次膨胀的内容会在后续所有调用里反复重发。**

> 已落地的前置优化：`agent链路耗时点优化.md` 第 1 节"按需加载工具提示词"（ToolRouter + CompactCatalogBuilder，规划阶段从全量 9 个工具降为按需 2 个）。本文档是第 2 节"上下文传递优化"的设计。

## 2. 上下文传递现状

### 2.1 调用链

```

        ↓ AfterAiHook PLANNING
TaskPlanner.decompose()
  └─ planner 调用（aliibabaChatClient）: user = toolsDescription + completedSummary(50/工具)
       + failedSummary + userInput + currentResponse(截200)
        ↓ SubTaskPlan
SubTaskAgent.execute()（subAgentChatClient，无 ChatMemory advisor）
  └─ subAgentChatClient.prompt().system(subagent).user(执行 prompt)
       .toolCallbacks(filterCallbacks) → .call()
        ↓ Spring AI function-calling 循环（每轮把工具结果追加进消息历史并全量重发）
      结果 → parseResult() 提取 ===DATA_SNAPSHOT=== → SubTaskResult
```

## 3. 膨胀根因分析（主 → 次）

### 3.1 主因：工具结果全量回灌（tool-call 循环重发）

Spring AI 的 function-calling 循环机制：每次工具执行后，把**工具返回的完整字符串**作为一条 `tool` 消息追加进对话历史，下一次 LLM 调用把**全部历史（system + user + 前面所有 assistant/tool 消息）**重新发送。

`BlogTool.queryPublishedBlogs()` 返回完整 `List<Blog>` 实体——每个 Blog 携带十几~二十个字段（`id/shopId/userId/title/images/content/liked/comments/createTime/updateTime/icon` 等），其中 `content` 是用户博客全文。10 条博客序列化后 ≈ **2,000 token**。

对应 trace 增量：第 2 轮 `+2,044`、第 3 轮 `+2,086`——正是博客列表结果被追加并重发。

**关键点**：膨胀的不是"一次调用"，而是**每次工具结果都永久进入消息历史，后续所有轮次都带着它重发**。削掉它，三次数值一起降。

#### ⚠ 取证进展：滚雪球已实证（2026-08-08 复审，trace `f56e69`）

第 2 轮增量 `+2,044` 可归因博客列表（~2,000 token）；但第 3 轮 `+2,086` **无法归因**——weather 结果只有一句 `"The weather in 长沙 is sunny"`（`WeatherQueryTool.java:25`，~10 token），`query-weather` 的 assistant tool_call 亦小。

**新证据（REST API 拉取 trace `f56e69a6…`，userId 1010，今日运行）**：子 agent 三次调用输入 `1,001 → 2,147 → 3,335`，**增量 `+1,146` / `+1,188` 几乎相等**——每次新轮次都重发一份约等于"前序工具结果"的载荷。weather 结果极小，第 3 轮 +1,188 不可能来自它，唯一合理的解释是 **provider 每轮把已发生的工具结果（或等价内容）重新计数/重发，上下文按轮次线性滚雪球**。这不只是"输入大"，而是**结构性累积**——工具数/轮数越多，膨胀越线性。

**结论**：4.1/4.2（截断）只把每轮增量从 ~2,000 降到 ~800，**不改变滚雪球结构**。根治需 §4.4 结构性方案（手动循环 + 结果压缩），把每轮增量压到 ~150（压缩摘要长度）。

### 3.2 次因：currentResponse 未截断

子 Agent 执行 prompt 里 `currentResponse`（"AI 已有回复"，即 Phase1 输出或上一轮子 Agent 摘要）**原样拼接**；作为 user prompt 的一部分，它在 tool-call 循环里每轮都重发。对比 planner 侧已截 200 字，子 Agent 侧缺失。

### 3.3 结构性因素：循环轮次多（本次不改）

执行 prompt 要求"每次只调用一个工具，等待返回结果后再调下一个"→ 两个工具需 3 轮全量重发。若允许并行 tool_call 可省 1 轮，但**改动执行语义、需实测 qwen-plus 并行稳定性，本次不做**（维持串行）。

**结构性边界（审查 B）**：Spring AI 内置循环每轮重发全部历史，累计输入 ≈ `Σ_j (n−j+1)·result_j`——工具条数越多，重发次数越多。§5 收益目标**仅在恰好 2 个工具时成立**；一次执行 4 个工具时末轮输入仍会线性涨。远期结构化解法（本次不做，建议写入路线图）：改手动循环，每轮把**已完成的旧工具结果压成一行摘要、只保留最新一条工具结果全文**，替代 Spring AI 内置循环的全量重发。

## 4. 方案设计（3 项核心改动 / 4 处文件改动）

### 4.1 框架层硬截断——工具结果在回灌进 LLM 前定型为小串

**目标**：任何工具的结果在进入消息历史前就截断，history 里存的是小串，之后每轮重发都是小串。这是覆盖全部工具的**安全网**。

> **与 4.2 分工（审查 F）**：4.1 = 安全网（恒成立、无脑兜底，防御未知/未来工具，即便 4.2 把所有已知工具都压了也保留）；4.2 = 质量优先（每个工具返回紧凑 DTO，主动做）。两者是同一收益的两种手段，真正贡献大头的通常是 4.2。

**改动**：

`GuardedToolCallback`（所有工具的唯一通道，`ToolBeanCollector.setApplicationContext()` L80-87 包装）：

```java
// call() ALLOW 分支
case ALLOW -> {
    ...
    String result = delegate.call(functionPayload, toolContext);
    return limitToolResult(result);          // ← 新增硬截断
}
// callBypass() 同理
```

- 新增构造参数 `maxResultChars`（默认 1200），由 `ToolBeanCollector` 注入。
- 截断是字符级（`substring(0, max) + "...(截断)"`）。LLM 把工具结果当文本读，不解析 JSON 结构，粗暴截断不影响摘要质量；`===DATA_SNAPSHOT===` 回显也因此变小（LLM 只能回显它看到的），`rawResults` 用于 50 字历史摘要，无影响。
- ⚠ **codepoint-safe（审查 I1）**：`String.substring` 在 emoji 等代理对上会切出孤立代理对，写入请求 JSON 变乱码。实现用 codepoint-safe 截断（`codePointCount` / `offsetByCodePoints`），并**顺带修**现有 `truncate()`（`TaskPlanner.java:502`、`SubAgentPromptBuilder.java:103` 已带此问题）。

**覆盖范围**（同一截断点自动生效）：
- 子 Agent 路径（主目标）
- 回退 `TaskExecutor.executeLlmReason()`（其 `contextSummary` 拼接即来自 guard 返回）
- CONFIRM 恢复路径 `executeApprovedTool()` → `callBypass()`
- guard 自身生成的 BLOCK/CONFIRM 消息是小 JSON，不受影响

**配置**：`PromptGuardProperties` 新增嵌套类 + YAML：

```yaml
hmdp:
  prompt-guard:
    tool-result:
      max-chars: 1200
```

**文件**：
- `src/main/java/com/hmdp/agent/guard/GuardedToolCallback.java`
- `src/main/java/com/hmdp/agent/tool/ToolBeanCollector.java`
- `src/main/java/com/hmdp/agent/config/PromptGuardProperties.java`
- `src/main/resources/application.yml`
- 构造点全仓仅 `ToolBeanCollector.setApplicationContext()` 一处（已核实 L80），新增构造参数无其它波及

### 4.2 工具层压缩——保质量，覆盖主要大返回工具

**目标**：框架层硬截断是兜底（防止任何工具炸上下文）；工具层压缩是**质量优先**的主动优化——让工具返回"LLM 够用的最小字段集"，而非截断后的残缺 JSON。**推广方向（审查 F / 审查追加）**：审查追加笔记"ai 拿到工具结果，貌似可以强制设置特定 dto，大部分工具返回结果太浪费 token 了"正是本条，可沉淀为**工具返回规范**——所有 `@Tool` 方法默认返回紧凑 DTO（最小字段集 + 条数上限 + 长文本截断），与路线图 §7.3"工具设计原则"的"返回精简"一致。

`BlogTool.queryPublishedBlogs()` 改为紧凑投影：

```java
public record BlogBrief(String title, String content, Integer liked, Long total) {}

@Tool(description = "……按点赞数降序返回前5条（标题+内容摘要+点赞数），并附总数。……")
public List<BlogBrief> queryPublishedBlogs(ToolContext toolContext) {
    long total = blogService.query().eq("user_id", userId).count();
    Page<Blog> page = blogService.query().eq("user_id", userId).orderByDesc("liked").page(new Page<>(1, 5));
    return page.getRecords().stream()
            .map(b -> new BlogBrief(b.getTitle(),
                    truncate(b.getContent(), 80), b.getLiked(), total))
            .toList();
}
```

- top-10 → **top-5**，字段从全部降为 `title / content(≤80) / liked / total`，一次结果从 ~2,000 token 降到 ~300。
- **`total` 保总量（审查 C）**：示例回答"当前发布的博客共有7篇"依赖全量数据；top-5 后 LLM 看不到总数，会退化为"前 5 篇"——这是产品语义变化，不是纯 token 优化。`total` 字段保住"共几篇"类信息，几乎不花 token。
- **统一描述（审查 C）**：改 DTO 时同步对齐 `@Tool` 描述与 javadoc（现不一致：javadoc 说"标题+内容+点赞数+发布时间"，`@Tool` 只说"标题、内容、点赞数"，`BlogTool.java:26`）。
- 返回类型改变不影响工具 schema（function schema 只含参数，不含返回类型）；子 Agent 只读序列化字符串，无下游依赖。

`queryBlogsByTitle()` 同样处理：加 limit（如 top-10）+ content 截断 + 附 total（当前 `like("title", title).list()` 无 limit，不限用户，可能返回大列表）。

**测试（审查 E，必改）**：`BlogToolTest.java` 三条现断言与本次改动冲突，需同步更新：
- `queryPublishedBlogs_should_return_user_blogs`（断言 `List<Blog>` 返回 1 条）→ 改断言 `List<BlogBrief>` 投影字段
- `queryPublishedBlogs_should_limit_to_10`（断言**分页大小 10**）→ 改断言分页 **5**
- `queryBlogsByTitle_should_return_matches`（断言 `List<Blog>`）→ 改断言紧凑投影 + content 截断

**文件**：`src/main/java/com/hmdp/agent/tool/impl/BlogTool.java`、`src/test/java/com/hmdp/agent/tool/impl/BlogToolTest.java`

```java

```

**文件**：
- `src/main/java/com/hmdp/agent/subagent/prompt/SubAgentPromptTemplate.java`（新增 `CURRENT_RESPONSE_MAX_LENGTH = 400`）
- `src/main/java/com/hmdp/agent/subagent/prompt/SubAgentPromptBuilder.java`（复用现有 `truncate()`）

**先测后定（审查 G）**：Phase1 输出通常几十~几百字，若本身 <400 字符，截断等于没做；它又是"多轮累积回复"，MAX_ROUNDS=5 下第 5 轮可能到 ~1,200 字符，截 400 才有意义。实现时在 `SubAgentPromptBuilder.buildVariables` 加一行 `log.debug` 打印 `currentResponse.length()`，用实测定阈值（planner 侧 200 的取值依据同样缺失，一并实测）。

### 4.4 结构性方案（第二阶段，根治滚雪球）：手动工具循环 + LLM 结果压缩

> 用户决定（2026-08-08）：**保留 LLM 驱动工具循环**（动态反馈有价值——"像用工具调研后给意见"），但**原始工具结果不进上下文**，改为**每步结果由 LLM 压缩成要点摘要后存入历史**。§3.1 的 trace 证据（`+1,146 / +1,188` 相等增量）表明滚雪球是结构性的，截断只能降常数；本方案把每轮增量压到压缩摘要长度（~150），O(1) 不随工具数/轮数涨。

**目标**：上下文历史只存 `assistant tool_call` + `tool 压缩摘要`，不存原始结果；LLM 仍每轮看到上一步摘要并决定下一步（动态反馈保留）；最终基于压缩摘要生成回答与快照。

**流程（替换 Spring AI 内置 tool-call 循环）**：

```
SubTaskAgent.execute()
  history = []                                // 只存 assistant(tool_call) + tool(压缩摘要)
  for round in 1..MAX_TOOL_ROUNDS(默认 6):
    resp = chatModel.call(system + user(执行 prompt) + history)     // 手动循环，带工具
    if resp 无 toolCalls → 最终回答 → parseResult(snapshot) → break
    for toolCall in resp.toolCalls:
      raw = guardedCallback.call(args, toolCtx)       // Java 执行（guard 已兜底截断 1200）
      compact = compress(raw, toolName)               // 独立微调用：LLM 压成 ≤80 字要点
      history += [assistant(toolCall), tool(compact)] // 只存压缩摘要
  超上限 → 以当前历史补一次总结
```

**关键决策**：

1. **压缩方式 = 独立微调用**（确定性强）：每工具结果执行后，一次短 LLM 调用「把下面的工具结果压缩成 ≤80 字要点摘要，供后续步骤使用」。输入 = guard 截断后的结果，输出 = 几十字，成本每工具 ~150 token。备选"同一轮 LLM 内联输出观察摘要"省调用但依赖 LLM 稳定性，第一版不做。
2. **历史只存压缩摘要**：raw 结果绝不进 history，滚雪球根除。压缩保留关键信息（数字/名称/状态/错误）。
3. **最终回答质量**：最终 LLM 基于压缩摘要总结；`===DATA_SNAPSHOT===` 回显压缩版数据，`rawResults` 仍用于跨轮 50 字历史摘要。
4. **循环上限**：`agent.subtask.max-tool-rounds`（默认 6）+ 每轮工具数上限，防失控。
5. **安全不变**：工具执行仍走 `GuardedToolCallback`（guard + permission）；CONFIRM 抛 `ConfirmRequiredException` 冒泡路径不变。

### 4.5 多轮对话总压缩（第三阶段，改进点）

> 用户补充（2026-08-09）：§4.4 只压缩**一次执行内**的工具调用；**多轮对话历史的总压缩**是另一层改进点。

**定位**：§4.4 管"轮内工具结果累积"；本节约的是**跨请求 / 跨轮次的对话历史累积**——用户与 AI 多轮对话时历史消息随对话增长，若整体回灌 LLM 上下文同样滚雪球。

**现状**：
- SSE Phase1 直连 `chatModel.stream`，无历史（断链修复 2026-08-03）；JSON 模式 advisor 已随 §6-H 移除 → **当前多轮记忆实际未回灌 LLM**。
- `agent_message` / `agent_conversation` 表存了会话历史，仅用于展示/查询，未回灌。
- 请求内 `MAX_ROUNDS=5` 的累积已有截断（planner currentResponse 200、子 agent 400、historySummary 50/工具），已部分受控。

**方案（对齐路线图 Phase 4）**：
- **Redis ChatMemory**（替代 JDBC，按 conversationId 隔离——顺带根治 §6 的 `"default"` 桶污染）。
- **SummarizingChatMemory**：消息数 > N 或 token > M 时，把**最旧一半**压成一段摘要，保留最新 N/2 条完整；每次请求注入 `[摘要] + [最近完整消息]`。
- **触发方式**：TokenBasedSummarizer（token 预算触发）或消息数触发，避免每轮重算。
- **回灌点需先设计**：多轮记忆回灌给谁——Phase1（`chatModel.stream` 前注入历史）还是 planner？当前架构刻意断链（每请求独立），"恢复哪层记忆"是产品/架构决策，需先定再做。
- **文件**：`AgentConfig`（Redis ChatMemory + SummarizingChatMemory Bean）、`AiServiceImpl`（回灌点）、复用 `agent_message` 历史。

**与 §4.4 关系**：两层独立、可并行——§4.4 管轮内工具结果，§4.5 管跨轮/跨请求对话历史。§4.5 前置是把多轮记忆回灌"接通"（当前是断的）。

## 审查意见（2026-08-08 设计评审）

> 已核对：`GuardedToolCallback` / `ToolBeanCollector` / `SubTaskAgent` / `SubAgentPromptBuilder` / `BlogTool` / `WeatherQueryTool` / `StatsQueryTool` / `TaskPlanner` / `TaskExecutor` / `AgentConfig` / `BlogToolTest`，以及两个 trace JSON。以下按严重程度排序。

### A. 最需先核实：§3.1 增量归因不自洽，收益表建立在其上

用已知工具尺寸验算 trace 的 token 增量：

| 轮次 | 输入 | 增量 | 按"每轮只追加新工具结果"模型应得 |
|------|------|------|--------------------------------|
| 1→2 | 1,001→3,045 | +2,044 | 博客结果(~2,000) + assistant tool_call(~44) ✓ 合理 |
| 2→3 | 3,045→5,131 | +2,086 | weather 结果≈"The weather in 长沙 is sunny"(~10 token, `WeatherQueryTool.java:25`) + assistant(~40) ≈ +50，实际却 +2,086 |

第 3 轮增量比"只追加 weather"多出约 2,000 token；而博客结果第 2 轮已计入历史，不该第 3 轮再产生 ~2,000 增量。文档把**两处增量都归到博客列表**，在已知工具尺寸下不成立。

可能真相（都未排除）：
- 博客结果序列化远大于 2,000 token，第 2 轮增量只反映部分；
- trace 存在未被捕获的消息增长（qwen 对整段历史重编码 / Spring AI 某轮全量注入工具 schema）；
- 隐藏重复执行（trace 中 `query-published-blogs` 的 guard span 仅一个，`json/trace-5e2f66f2…` 有单条，可能性低）。

两个 trace 输入序列完全一致（1,001/3,045/5,131），非噪声。**收益表（~57% 削减）完全依赖"增长 = 工具结果重发"这一归因**。落地前先取证：在 `SubTaskAgent.executeWithRetry` 每轮打印请求 message 条数 + 序列化长度（或 Langfuse 开启 input 捕获），重跑"查看我的博客以及长沙天气"。若第 3 轮真实增长点是别的，4.1/4.2 可能达不到宣称收益。

### B. 结构性：截断只降常数，不解决工具循环内的累积重发

4.1 把单条工具结果封顶 1,200 字符，但 Spring AI tool-call 循环每轮重发**全部历史**，总量为 `Σ_j (n−j+1)·result_j`——工具条数越多，重发次数越多。收益目标 ~1,300/~1,600 只在**恰好 2 个工具**时成立；一次执行 4 个工具时末轮输入仍线性涨到 ~2,500+。§3.3 只回避了"并行"，没提另一个结构性解法：**每轮把已完成的旧工具消息压成一行摘要、只保留最新一条工具结果全文**（改手动循环，不用 Spring AI 内置循环）。不必本次做，但建议写入 §3.3 或路线图，并明确收益目标适用范围为"2 工具场景"。

### C. top-10→top-5 有回答质量回退，建议补 total 字段

`agent链路耗时点优化.md` 示例回答"当前发布的博客共有7篇"说明 LLM 现在能看到**全量**。改 top-5 + content≤80 后 LLM 看不到总数，回答退化为"前 5 篇"——这是产品语义变化，不只是 token 优化。建议 `BlogBrief` 加 `total` 字段（或配套 count），保住"共几篇"类总量信息，几乎不花 token。同时改 DTO 时统一 `@Tool` 描述与 javadoc 的不一致（javadoc 说"标题+内容+点赞数+发布时间"，`@Tool` 只说"标题、内容、点赞数"，`BlogTool.java:26`）。

### D. 收益表只算输入 token，漏了输出 token 同样会降

第 3 次调用输出 425 token 含大段 `===DATA_SNAPSHOT===` 回显（LLM 复述它看到的工具数据）。输入一截，回显跟着小，输出 token 同步下降——qwen 按输入+输出计费，此收益未量化。建议收益表加输出列，(12:1) 比值也应结合输出一起算。

### E. 文件清单漏了测试，4.2 改动会直接挂掉现有单测

`BlogToolTest.java` 现有断言全部与 4.2 冲突：
- `queryPublishedBlogs_should_return_user_blogs`（断言 `List<Blog>` 返回 1 条）
- `queryPublishedBlogs_should_limit_to_10`（断言**分页大小 10**）
- `queryBlogsByTitle_should_return_matches`（断言 `List<Blog>`）

4.2 改 `List<BlogBrief>` + top-5 后三条必挂。§4.2"文件"只列 `BlogTool.java`，建议补测试更新（断言投影字段、分页 5、content 截断）。4.1 新增构造参数基本无波及——全仓 `new GuardedToolCallback` 仅 `ToolBeanCollector` 一处（已确认），文档"同步更新其它调用点(如测试)"属未核过的多余担心。

### F. 4.1 与 4.2 职责重叠，收益归因不清；"审查追加"笔记应并入正文

若 4.2 把博客结果压到 ~300 字符，4.1 的 1,200 上限**几乎不会触发**——两者是同一收益的两种手段，真正贡献 ~57% 的是 4.2，4.1 只是兜底（防御未知/未来工具）。文档把收益统一记在"工具结果截断(4.1+4.2)"上，掩盖了职责。建议明说：**4.1 = 安全网（恒成立、无脑），4.2 = 质量优先（每工具紧凑 DTO，主动做）**。这样正好把"审查追加"那条游离笔记（强制 DTO）并入正文——它就是 4.2 的泛化方向。

### G. 4.3 currentResponse 截 400 的收益存疑，先测后定

§3.2 列它为"次因"但没给实际尺寸。Phase1 输出通常几十~几百字，若本身 <400 字符，截断等于没做；它是"多轮累积回复"，MAX_ROUNDS=5 下第 5 轮可能到 ~1,200 字符，截 400 才有意义。建议在 `SubAgentPromptBuilder.buildVariables` 加一行 `log.debug` 打印 `currentResponse.length()`，用实测定阈值（planner 侧 200 的取值依据同样缺失）。

### H. §6 ChatMemory "default" 桶：断言"表基本为空"但没给验证方式

`MessageChatMemoryAdvisor` 未设 conversationId，`AgentConfig.java:111` 每次 planner/Phase1/LLM_REASON 调用都会读写 `"default"` 桶并**落库** `chat_memory` 表（窗口 10 条）。断言表空是对的（planner 输入稳定 ~2.6k 佐证），但建议 §8 验证补一条 `SELECT COUNT(*) FROM chat_memory WHERE conversation_id='default'`——一旦有数据，所有用户/所有请求的 planner 与 Phase1 都会注入彼此历史，是真正的跨用户污染，不只是 token 放大。既然多轮记忆本就没生效，顺手移除 advisor 是零回归最小修复，比推到 Phase 4 更稳。

### I. 细节与一致性

1. **字符级 `substring` 截断的 surrogate 问题**：在 emoji 上会切出孤立代理对，写入请求 JSON 变乱码。现有 `truncate()` 已带此问题，新截断点会放大；至少注明，或改 codepoint-safe。
2. **三套截断阈值语义不清**：guard 1,200（LLM 看到什么）→ snapshot 回显（LLM 决定）→ `parseResult` 500/数据（`SubTaskAgent.java:261`，存什么）。建议文档画清三级职责，避免后人困惑。
3. **§4 标题"3 项核心改动"**：含 queryBlogsByTitle 实为 4 处，建议改"4 项"或拆分。
4. **收益表数学自洽**（1−3901/9177≈57% ✓），但分母含可疑的 +2,086，见 A。

### 总结

方向正确、分层合理（guard 兜底 + 工具紧凑 DTO + currentResponse 截断），§6 附注诚实。但**核心收益论证建立在未经证实的增量归因上**（A），建议先取证再定收益目标；同时补上累积重发的结构性边界（B）、top-5 的 total 保底（C）、测试文件清单（E），设计即扎实。
