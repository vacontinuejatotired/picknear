## 1. 现状盘点：Langfuse 到底"硬"在哪里

### 1.1 数据链路（传输层已是标准协议，本身不绑平台）

```
Micrometer Observation（AgentTracer 业务埋点 + Spring AI 内置 LLM 层）
  → micrometer-tracing-bridge-otel（OTel bridge，span 标准化）
  → OTel SDK BatchSpanProcessor（异步批处理，导出失败不影响业务）
  → OtlpHttpSpanExporter（opentelemetry-exporter-otlp）
  → OTLP HTTP/protobuf（标准 GenAI 语义 gen_ai.*）
  → 观测后端（当前：Langfuse 云 OTLP 端点）
```

**关键结论**：业务埋点层（`AgentTracer` / `AgentSpanImpl` / `SpanLifecycle` / `SpanContext` / `ObservedSseEmitter` / `AgentField`）**只依赖 Micrometer Observation 抽象，代码里不含任何 langfuse 类引用**——Micrometer + OTel 本身就是"观测协议抽象层"，数据是标准化的。换展示端天然可行，不需要动埋点 API。

### 1.2 真正的 Langfuse 硬依赖清单（改造对象）

| # | 绑定点 | 位置 | 性质 | 换平台时的问题 |
|---|--------|------|------|---------------|
| B1 | OTLP 端点 / 鉴权头 / 专有 header 直指 Langfuse | `application.yaml` `management.otlp.tracing.*` | 配置硬编码：`${LANGFUSE_BASE_URL}/api/public/otel/v1/traces`、`Authorization: Basic`、`x-langfuse-ingestion-version: 4` | 换后端要手改 yaml，且 Langfuse 专有 header/端点格式（必须带 `/v1/traces`）散落成隐性知识 |
| B2 | **LLM generation 名字带功能前缀**（`mark()` ThreadLocal 打标） | `ChatModelObservationConventionConfig` | 为"Langfuse 不展示自定义属性 → 把调用方/任务编码进 span 名可见"而设计；打标调用点散落在 **6 个业务类**（`AiServiceImpl`/`StreamingChatInvoker`/`PlanSupport`/`TaskExecutor`/`AbstractToolLoop`/`ToolResultCompressor`，见 13.3.1 明细；`SubTaskAgent` 仅有 `clear()` 非打标方），且标识符是业务代码里的魔法字符串 | 换 Jaeger/Tempo/SigNoz 等支持 attributes 的后端时，该前缀变成冗余噪音；换另一个"不展示属性"的后端时又需要同样的编码；魔法字符串散落属「隐性约定」同类物 |
| B3 | **LLM content 补发**（`gen_ai.request/response.content`） | `ChatModelObservationConventionConfig` | 为"Langfuse input/output 恒为 null"而补发；Spring AI 默认 convention 不发 | 该能力本身是 OTel 标准属性，应保留；但开关语义（默认 true）绑定 Langfuse 渲染需求 |
| B4 | **业务 span 语义编码进 span 名**（`agent.tool_call.queryShop`） | `AgentSpanSpec.spanName()` + `AgentTracer.start()` + **`guard/ToolGuardGate` 的 `buildGuardSemantic()`/`compactArgs()`/`ARGS_MAX_CHARS`（为 span 名编码特制的载荷加工，污染业务守卫类）** | 为"Langfuse 转译丢 attributes，语义要进 span 名才可见"（2026-08-03 实测） | 支持 attributes 的后端应改为靠属性展示，语义后缀变成噪音；命名策略必须按后端能力可开关；载荷加工属行为适配层，须从业务类下沉（13.3.2） |
| B5 | **观测白名单（前缀过滤）** | `ObservabilityTraceFilter` | 动机是"省 Langfuse Hobby 50k 配额"（task observation 全量上云约 21.6 万 units/月） | 白名单能力本身平台无关（控制任何后端的导出量 + 本地减噪），但"为省 Langfuse 配额"的语境与默认策略应泛化 |
| B6 | 会话/用户关联属性约定 | `AgentField.USER_ID`（`user.id`）等 | 架构文档 §6.5 提到根 span 应带 `langfuse.session.id`/`langfuse.user.id`，当前实现用了通用 `user.id`/`conversation.id` | 不同后端的关联约定不同（Langfuse 认 `langfuse.user.id`；SigNoz 认 `session.id`…），需要"关联属性映射"策略 |
| B7 | 语义开关语料绑定 Langfuse | `TraceProperties`（`include-content` 注释/默认值） | 注释与默认值语义绑定 Langfuse 渲染 | 文案/默认值应平台中立 |
| B8 | 注释/日志散落 Langfuse 字样 | `AgentSpanSpec`、`ObservedSseEmitter`、`ToolGuardGate`、`AttributeSanitizer` 等 72 处 | 无功能影响 | 清理项，保持代码自解释 |
| B9 | **（配套，非链路观测）Prompt 远端仓库直连 Langfuse REST API** | `LangfusePromptRepository`（Prompt Management） | 独立于链路观测的另一处 Langfuse 依赖 | 若只切观测后端不改这里，Prompt Management 仍走 Langfuse；**本次评审决策：一并抽象（§4.5）** |
| B10 | 无后端时不可运行 | `application.yaml` 未配置环境变量时 endpoint 变非法相对路径，OTLP 导出失败告警刷屏 | 环境依赖隐性 | 需要一等公民的 `noop` / `console` 本地后端 |

### 1.3 结论

- 传输层已经解耦（OTLP 标准协议），**不需要也不能推翻**——Micrometer + OTel 就是约定的"观测抽象层"。
- 需要解耦的是**两层**：
  1. **接入参数层**（B1/B10）：导出去哪里、带什么鉴权头 → 泛化为"观测后端"接入配置。
  2. **行为适配层**（B2/B3/B4/B5/B6/B7）：为了让数据在"某一个后端"里好看/省配额而做的特化行为 → 泛化为"后端能力"驱动的策略开关。

## 2. 目标与改造原则

### 2.1 目标

1. **可插拔（观测）**：通过配置（不重编译）切换观测后端：`langfuse` / `jaeger` / `signoz` / 通用 `otlp-collector` / 本地 `console` / 关闭 `noop`。
2. **可插拔（Prompt 仓库）**：通过 `agent.prompt.repository.type` 切换提示词远端仓库：`langfuse` / 预留 `db` / `none`（Fail-Open 内置）。
3. **新增平台零改动业务代码**：新增后端只加一个实现类 + 枚举项 + 配置段（OCP）。
4. **现有能力不丢**：自定义属性仍全量写入 OTel span；InMemorySpanExporter 集成测试（M2.5）不破坏。
5. **Fail-Open 保持**：后端缺失/失配/导出失败都不能影响主链路。
6. **远程观察会话关联、脱敏统一出口保持不变**（AttributeSanitizer 是平台无关的必须项）。

### 2.2 戒律（评审红线）

- **不接管 Boot 的 exporter 自动装配**：`management.otlp.tracing.*` 是 Spring Boot 原生能力，代码接管会产生装配漂移风险。`TraceBackend` **只提供能力描述与关联属性映射**，不含 endpoint/headers（接入参数唯一事实源 = yaml，13.2.1），不 create/register SpanExporter。
- **不改业务埋点调用方式**：`agentTracer.start(AgentSpanSpec.X, semantic)` API 形态不变，埋点方零改动。
- **「是否打标/是否拼名」的条件永不进业务代码**（评审 13.3.1 铁律）：`mark()` 调用保留在业务侧（引用 `CallerType` 枚举），忽略与否由 Convention/命名策略内部按能力决定——禁止把「要不要观测」的判断下放进业务类。
- **语义内容留业务侧、加工格式沉策略侧**（评审 13.3.2 铁律）：guard 的 decision/toolName/modelName/payload 等原始语义由业务侧传出；拼法/脱敏/限长等 span 名载荷加工一律在 `SpanNameEncoder`。
- **保持既有配置兼容**：旧的 `hmdp.ai-observability.chat-observation.include-content` 等开关继续生效（新能力开关默认值对齐现状=Langfuse 行为）。
- **语义数据永远进属性**：无论命名策略是否开启，`AgentField` 属性照常全量写入（数据标准不丢，换后端即得）。

## 3. 总体设计（两层解耦）

### 3.1 架构图

```
┌─ picknear (8081) ────────────────────────────────────────────────┐
│ ① 业务埋点（AgentTracer + AgentField：平台无关，已解耦）           │
│ ② 行为适配层（★ 本次改造核心，策略化）                            │
│    TraceBackend.capabilities() 决定：                             │
│      - 是否语义命名（B4） / 是否打功能前缀（B2）                   │
│      - 是否补发 content（B3） / 白名单默认策略（B5）              │
│      - 会话关联属性映射（B6）                                     │
│ ③ 传输（Micrometer Observation → OTel → OTLP，标准协议，不动）    │
│    endpoint/headers 唯一事实源 = management.otlp.tracing.* yaml    │
│    （接口不持接入参数，评审 13.2.1 收敛）                            │
└──────────────┬────────────────────────────────────────────────────┘
               ▼ OTLP（HTTP/protobuf，标准协议）
      本次：应用直连后端（management.otlp.tracing.endpoint 指向目标后端）
      ┌──────┬──────────────────────────┬──────────────────────┐
      ▼      ▼                          ▼                      ▼
  Langfuse   Jaeger（本地）        SigNoz/Tempo/通用 OTLP     noop/console（本地）
（默认实现）  （换后端只改 endpoint/环境变量）
      └── 后续增强路径：可插入 OTel Collector 中间层，应用固定发 collector，
          后端路由/凭据下沉到 collector 配置（§3.2 形态 A）
```

### 3.2 两个可选接入形态

| 形态 | 做法 | 换后端成本 | 适用 |
|------|------|-----------|------|
| **B. 应用直连后端（✅ 本次采用）** | `management.otlp.tracing.endpoint/headers` 按后端 profile/环境变量切换（或 Boot 3.4 的 `management.otlp.tracing.exporters.<id>` 多导出器） | 改环境变量/重启应用 | 当前唯一后端、演示/开发期轻量场景；改造面最小 |
| **A. OTel Collector 中间层（🛤 后续增强，本次不做）** | 应用固定指向本地 collector (`http://localhost:4318/v1/traces`，无鉴权)；**后端是谁、鉴权凭据全部下沉到 collector 配置** | 只改 collector yaml（pipeline 的 endpoint/headers），应用零改动零重启 | 生产、多后端并存、凭据不进应用配置 |

> 两条形态共存：代码层的 `TraceBackend` 抽象在两种形态下都生效（行为适配不依赖接入形态）；接入形态只影响 `management.*`/collector 配置怎么写。**本次先落地 B**，架构上预留 A 的路径（config 与文档层面说明，不引入 collector 容器）。

## 4. 核心抽象设计（设计模式落地）

### 4.1 `TraceBackend` —— 观测后端策略（策略模式）

> **v1.2（评审 13.2.1 吸收）**：接口只承载**行为适配决策**（能力 + 关联映射），**不承载接入参数**——`endpoint()/headers` 从接口移除，接入参数唯一事实源 = `management.otlp.tracing.*` yaml / 环境变量（形态 A 时下沉 collector）。消除「实现类一份、yaml 一份」的双事实源；接口内聚，与 §3.1「传输层不动、接入参数层走配置」严格一致。

```java
public interface TraceBackend {
    /** 平台标识：langfuse / jaeger / signoz / collector / console / noop */
    String id();

    /** 平台能力描述 —— 行为适配层的决策依据 */
    TraceBackendCapabilities capabilities();

    /**
     * 根 span 会话/用户关联属性（平台关联约定，如 Langfuse 认 langfuse.user.id、
     * SigNoz 认 session.id）。
     * 边界（评审 13.2.4）：v1.2 为静态映射 MVP —— 值复用现有 AgentField 相关属性值
     * （user.id / conversation.id），落点默认根 span attributes；后续后端差异扩展为
     * 「关联属性描述符」（属性名 + 值提取 + 落点），不在本接口新增 Map 键。
     */
    Map<String, String> associationAttributes();
}

public class TraceBackendCapabilities {
    /** 自定义属性在目标后端 UI 是否可见 —— 唯一事实源（评审 13.2.2） */
    boolean supportsSpanAttributes;
    /** 是否需补发 gen_ai.request/response.content（OTel 标准属性，默认 true） */
    boolean contentSupplementRequired = true;
    /** 是否有配额限制（→ 白名单默认严谨度、默认采样；默认 false=不感知） */
    boolean quotaAware = false;
    /** 该后端默认放行的 span 前缀（agent. 项由 AgentSpanSpec.NAMESPACE 常量派生，评审 13.3.3） */
    List<String> defaultTracePrefixes = List.of(AgentSpanSpec.NAMESPACE, "spring.ai.", "gen_ai.");
    // 注意：semanticNameEncodingRequired 不在此列 —— 由命名策略从 supportsSpanAttributes 推导
    // （semanticNameEncodingRequired = !supportsSpanAttributes），杜绝布尔互生失配（评审 13.2.2）。
}
```

- **LangfuseBackend**（现状对齐）：`supportsSpanAttributes=false`、`contentSupplementRequired=true`、`quotaAware=true`（语义编码经推导开启；content 补发开启；白名单严谨）。
- **JaegerBackend / SignozBackend / Tempo 通用后端**：`supportsSpanAttributes=true`、`contentSupplementRequired=true`、`quotaAware=false`（语义编码经推导关闭，语义靠 attributes 展示；content 补发是 OTel 标准属性，默认开）。
- **OtlpCollectorBackend**（通用直连，接入参数全部走 yaml/环境变量，平台中立）。
- **ConsoleBackend**：本地调试，无外部依赖；**NoopBackend**：`traceEnabled=false` 等效。
- **接入参数（endpoint/headers）一律不写进实现类**：由 `management.otlp.tracing.*` yaml（`${LANGFUSE_BASE_URL}` 等环境变量注入）承载；后端实现类不含任何 URL/凭据/专有 header 字面量。

### 4.2 后端装配 —— 收敛为「Spring 收集 + 单装配器」（工厂模式，评审 13.2.3 吸收）

> **v1.2**：不再手写「枚举 → 实现」注册表（与 Spring 容器双实例并存，层叠床架屋）。装配改为：各 `TraceBackend` 实现以 `@Component` 注册，装配器注入 `Map<String, TraceBackend>`（key=bean 名或 id）按配置选择；**唯一保留的决策职责 = 未知 type / 实现缺失 → 降级 Noop**。

```java
@Component
public class TraceBackendAssembler {          // 原名 TraceBackendFactory，降级为单装配器（非接口）
    private final Map<String, TraceBackend> backends;   // Spring 按 id() 汇总注入

    public TraceBackend assemble(BackendProperties props) {   // Fail-Open 分级见下
        TraceBackend backend = backends.get(props.getType());
        return backend != null ? backend : NoopBackend.INSTANCE;
    }
}
```

- 新增后端 = 新增 `XxxBackend` 实现（`@Component` + `id()`）+ `TraceBackendType` 枚举一项 + yaml 一段配置。**无需改装配器**（Map 自动收集），业务埋点零改动（OCP）。
- **Fail-Open 分级（评审 13.4-1，消除 §4.2 与 §9 S2 的矛盾）**：

| 情形 | 行为 | 理由 |
|------|------|------|
| `type` 缺省 | **Langfuse**（兼容现状默认） | 与现状配置等价，回归基线一致 |
| `type=noop` | 整门面 Noop 空转（等价 `trace-enabled=false`） | 显式关闭 |
| `type=未知值` / 实现类缺失 / 装配异常 | 降级 **NoopBackend**（WARN 日志） | Fail-Open，不影响主链路 |
| `type` 合法但**接入参数缺失**（如 langfuse 未配 base-url） | **不降级**：埋点照常、导出失败告警（现状路径 B10） | Fail-Open 不掩盖配置错误；由 noop/console 显式关闭 |

### 4.3 行为适配改为"能力驱动"（适配器 + 策略）

把 B2/B3/B4/B5/B6 的"为了 Langfuse"实现，改为读取 `backend.capabilities()`：

| 行为 | 现状（Langfuse 特化） | 改造后（能力驱动） |
|------|----------------------|-------------------|
| 业务 span 语义命名（B4） | `AgentSpanSpec.spanName(semantic)` 无条件拼语义后缀；**`ToolGuardGate` 在业务类里做载荷加工**（`buildGuardSemantic`/`compactArgs`/`ARGS_MAX_CHARS`） | `SpanNamingStrategy` 从语义输入生成完整 span 名：`capabilities.supportsSpanAttributes ? 不拼 : 拼`；**guard 的「语义内容」（decision/toolName/modelName/payload）留在业务侧传原始值，「加工格式」（拼法/脱敏/限长）下沉 `SpanNameEncoder`**（评审 13.3.2：语义留业务、加工沉策略）；属性照常全量写入 |
| LLM generation 功能名 + 打标（B2） | 6 个业务类里散落 `mark("phase1")` 等**魔法字符串**，`getContextualName` 无条件加前缀 | 打标调用点收敛为 **`CallerType` 枚举常量**（观测包定义：`PHASE1/PLANNER/LLM_REASON/SUBAGENT_EXEC/SUBAGENT_COMPRESS`，业务类引用枚举）；`getContextualName` 仅在 `semanticNameEncodingRequired` 时拼前缀，否则保持 `chat <model>`（语义已在 attributes）；**铁律：能力开关关闭时 `mark()` 调用保留在业务代码、忽略与否由 Convention 内部决定，禁止把「是否打标」条件放进业务代码**（评审 13.3.1） |
| LLM content 补发（B3） | 无条件补发（开关 `include-content`） | 补发开关改为 `capabilities.contentSupplementRequired AND 用户开关`（向后兼容：默认对齐 Langfuse 现状） |
| 白名单默认策略（B5） | 前缀写死 `agent./spring.ai./gen_ai.`（注释绑定 Langfuse 配额） | 默认前缀由 `capabilities.defaultTracePrefixes` 提供，其中 `agent.` 项由 `AgentSpanSpec.NAMESPACE` 常量派生（评审 13.3.3，消除三处事实源）；合并语义 = **backend 默认 + 用户追加，用户不可删除默认项**（评审 13.4-2）；quotaAware 后端默认严谨、本地 console 可放宽 |
| 会话/用户关联（B6） | 属性 `user.id`/`conversation.id`（通用名） | 根 span 按 `backend.associationAttributes()` 额外写入平台关联属性（如 Langfuse 的 `langfuse.user.id`/`langfuse.session.id`）；值复用现有 `AgentField` 属性值、落点根 span attributes（评审 13.2.4） |

> 建设性后果：换到 Jaeger 后：
> - 语义编码关闭 → span 名回归无噪音的 `agent.tool_call`，语义通过 attributes 展示；
> - content 补发保留 → trace 里能看到完整 LLM 输入输出（Jaeger 原生展示 attributes）；
> - 白名单仍然生效 → 本地开发自此后端零配额顾虑、日志更干净。

### 4.4 依赖方向（DIP 检查）

```
埋点方（ChatController/AiServiceImpl/TaskPlanner/SubTaskAgent）   —— 只依赖 AgentTracer/AgentField（不变）
AgentTracer / Convention / 白名单 / 命名策略                       —— 只依赖 TraceBackend 抽象（新增）
TraceBackend 的实现                                                 —— 承载平台能力差异（接入参数在 yaml，不在此层，13.2.1）
```

一切 Langfuse 形态只允许出现在三处叶子：`backend/impl/LangfuseBackend`（能力）、`prompt/repo/LangfusePromptRepository`（Prompt 仓库实现）、`management.otlp.tracing.*` yaml（接入参数）；其余代码禁提平台名。

### 4.5 Prompt 远端仓库抽象（B9 一并解耦，评审决策 ②）

Prompt Management 是**独立于链路观测**的 Langfuse 依赖（直连 Langfuse REST API 拉取/推送模板），决策将其纳入本次一并抽象：

```java
/** 远端提示词仓库 —— 策略接口（顶层只面向本接口编程） */
public interface RemotePromptRepository {
    Optional<String> fetch(String key);     // 拉取模板（含成功/404 负缓存、瞬时失败熔断 —— 现逻辑整体搬入）
    boolean seed(String key, String content);// 推送模板（创建/新版本）
    void evictAll();                        // 清缓存（管理端点用）
}

/** 提示词仓库装配器（普通类，非接口 —— 评审 13.2.3：工厂本身无人替换，接口化 YAGNI）。
 * 按 agent.prompt.repository.type 装配；未配置/缺参数 → 无远程（Noop，Fail-Open）。 */
@Component
public class PromptRepositoryAssembler {
    public Optional<RemotePromptRepository> assemble(PromptProperties props) { ... }
}
```

- **实现**：`LangfusePromptRepository implements RemotePromptRepository`（现文件整体平移，类名可保留或改 `LangfuseRemotePromptRepository`）；预留 `DbPromptRepository`（MySQL 落库）为未来实现。
- **调用面改动（小）**：`DefaultPromptService` / `PromptCacheWarmer` / `PromptSeeder` / `PromptAdminController` 依赖类型从 `LangfusePromptRepository` 换为 `RemotePromptRepository`；构造处由装配器按配置注入（未配置 `repository.type` 或 `base-url` 空 → 注入 Noop 实现，行为与现状"未配置即 Fail-Open 走内置"一致）。
- **超时熔断/双缓存等既有健壮性逻辑不动**，只动"谁被依赖"与"从哪装配"。

## 5. 设计模式映射表（给评审/面试用）

| 模式 | 落点 | 解决的问题 |
|------|------|-----------|
| **策略模式** | `TraceBackend` 接口 + 各后端实现 | 同一套埋点数据在不同平台的差异化处理策略可替换 |
| **能力接口归一**（原"适配器"，评审 13.2.3 改述） | 每个后端 x → 统一 `TraceBackend.capabilities()/associationAttributes()` | 把平台差异翻译成统一能力接口，上层只面向能力编程 |
| **依赖倒置（DIP）** | 上层全部依赖 `TraceBackend` / `RemotePromptRepository` 抽象 | 行为不再依赖具体平台类；Langfuse 细节隔离在叶子实现 |
| **开闭原则（OCP）** | 新增后端只加实现类+枚举+配置（`Map` 自动收集，无需改装配器） | 平台扩展不修改任何业务埋点代码 |
| **枚举收敛（评审 13.3.1）** | `CallerType` 枚举取代 6 处业务代码里的打标魔法字符串 | 调用方标识有单一事实源，展示层拼名直接引用 |
| **状态/降级（Fail-Open 分级）** | 装配器按 type 选择，未知/缺失/异常 → `NoopBackend`；`type` 缺省 → Langfuse（兼容现状）；参数缺失不降级（13.4-1） | 与现有"埋点 Fail-Open"先例对齐，且不掩盖配置错误 |
| **策略/装配（Prompt 仓库）** | `RemotePromptRepository` 接口 + `PromptRepositoryAssembler`（普通类） | 与观测后端同一套路：Langfuse 只是提示词仓库的一个实现，未来可换 DB/Nacos |

### 13.2 设计模式问题

#### 13.2.1 【重要】`TraceBackend` 接口职责混杂，且 `endpoint()` 是无人消费的悬空方法

`TraceBackend` 一个接口同时承载三件事：**能力元数据**（`capabilities()`）、**接入参数**（`endpoint()`/`headers`）、**关联属性映射**（`associationAttributes()`）。问题出在这三者的生命周期完全不同：

- 能力与关联映射是**行为适配层的决策依据**，由上层消费，有意义；
- 而 `endpoint()` 在 §2.2 戒律「不接管 Boot 的 exporter 自动装配」的前提下**没有任何消费者**——Boot 的导出配置只从 `management.otlp.tracing.*` yaml 读取，`TraceBackend.endpoint()` 至多用于启动期校验或文档。

于是同一个接入参数出现**两份事实源**：`LangfuseBackend` 代码里写死 `/api/public/otel/v1/traces + Basic + x-langfuse-ingestion-version:4`（§4.1），§6.2 的 yaml 里又原样写一遍。换后端/改端点时改一处漏一处，恰好会复现 B1 想消灭的「隐性知识散落」问题，只是从 yaml 挪到了实现类 + yaml 两处。

**建议**（二选一）：

- **收敛方案**：`TraceBackend` 只保留 `id() + capabilities() + associationAttributes()`，`endpoint()/headers` 彻底交给 yaml（Boot 原生属性 + 环境变量切换，形态 A 时下沉 collector）。这样接口内聚，「行为适配」与「接入参数」两个解耦层严格分离，也符合 §3.1 架构图里「传输层不动」的表述。
- 若坚持保留 `endpoint()`：必须在文档写明它的**唯一消费者**（例如启动期 `ObjectProvider` 注入后做配置校验 + 告警，或生成 `management.otlp` 的动态 `EnvironmentPostProcessor` 注入），并明确「测试环境以 yaml 为准 / 以 endpoint() 为准」的同步约束——否则实施时它必然退化为死代码。

#### 13.2.2 `TraceBackendCapabilities` 两个布尔字段互生但并列

`supportsSpanAttributes` 与 `semanticNameEncodingRequired`（`= !supportsSpanAttributes`，§4.1 注释自己写了推导关系）是同一事实的两种表述，却并列建档。新增后端实现时极易只改其中一个导致失配（例如声明 `supportsSpanAttributes=true` 却忘改 `semanticNameEncodingRequired=false`，于是 span 名继续带语义后缀——正是本方案想消除的噪音）。

**建议**：单一事实源。要么只保留 `supportsSpanAttributes`，`semanticNameEncodingRequired` 由命名策略内部推导；要么用枚举表达三级模式（如 `semanticEncoding: NONE | ENCODED`），杜绝布尔横跳。同时给每个能力配用户级覆盖开关（§6.1 已对 `semantic-encoding` 做 auto/true/false 三态，`contentSupplement`/`quotaAware` 建议同样处理），避免「新增后端 → 新增能力维度 → 上层消费代码加分支」的扩展性反噬。

#### 13.2.3 装配层叠床架屋：手写工厂注册表 + Spring 容器 + AutoConfiguration 三方并存

三处职责重叠：`TraceBackendFactory`（手写枚举→实现注册表，§4.2 要求扩展时「工厂注册一行」）、`TraceBackendAutoConfiguration`（§7.1 又要「装配 backend bean + 暴露给上层」）、Spring 自身的 `@Component` 扫描。未说明三者分工，实施时容易出现「工厂里 new 实现」与「Spring 容器里又有一个同 type 的 bean」双实例并存。

Spring 环境里更自然的写法是 `List<TraceBackend>` / `Map<String, TraceBackend>` 注入后按 `id()` 索引——新增后端**只加实现类 + 枚举 + 配置**即可自动收集，连方案里「工厂注册一行」都可省去，比目前更贴合 §2.1「新增平台零改动」与 OCP 表述。手写注册表的核心价值只剩「未知 type / 实现缺失 → 降级 Noop」这一条决策，这部分保留为工厂/装配器的单一职责即可（建议：AutoConfiguration 持有工厂，一个装配入口，二选一合并）。

同类的过度抽象：§4.5 把 `PromptRepositoryFactory` 定义为**接口**（无人会替换工厂本身）、§5 把 `SpanNamingStrategy` 的**模板方法**列为「可选」——命名策略实际只有「拼/不拼、怎么拼」两三个动作，用不上模板方法；工厂接口化属 YAGNI。建议 §5 模式映射表收敛：删去模板方法一行；「适配器模式」一词建议删去或改述为「能力接口归一」（`TraceBackend` 被同时冠以策略+适配器，恰是指标职责边界模糊的信号，见 13.2.1）。

#### 13.2.4 【次要】`associationAttributes()` 的 `Map<String,String>` 表达能力边界

静态键值对只能表达「额外写哪些 key」，表达不了：值从哪来（现有 `user.id` 的值来自 Controller 的 userId 参数，§6.1 关联映射要复用同一值源）；以及不同后端对「会话关联」的识别落点差异（span attributes / resource attributes / 专有字段，B6 表格自己列举了 Langfuse 认 `langfuse.*`、SigNoz 认 `session.id`）。本次按静态映射 MVP 落地可接受，但文档须写明边界：映射值仍复用现有 `AgentField` 相关属性值，落点默认根 span attributes；后续后端差异扩展为「关联属性描述符」（属性名 + 值提取 + 落点）而不是再加一个 Map。

### 13.3 业务代码硬编码清单（按你的口径：配置文件/单独观测实现类不算，业务代码里的才算）

按此口径核对后，**yaml 里的 endpoint/headers/ingestion-version、`LangfuseBackend`（单独实现类）、`ObservabilityTraceFilter` 的默认前缀常量（观测实现类）、`LangfusePromptRepository` 内部的 API 路径、72 处注释**——全部不算硬编码，方案对它们的处理（收敛进实现类 / 统一清理）合理，无需改动。真正落在**业务代码**里的平台痕迹有三处，其中两处是方案的**明确遗漏**：

| `StreamingChatInvoker` (§75) | `mark("phase1")` |
| `PlanSupport` (§78) | `mark("planner")` |
| `TaskExecutor` (§148) | `mark("llm-reason")` |
| `AbstractToolLoop` (§133) | `mark("subagent-exec", taskLabel)` |
| `ToolResultCompressor` (§43) | `mark("subagent-compress", toolName)` |

这些 caller 标识符是**写在业务代码里的魔法字符串**，且经过 `getContextualName` 拼进 generation 名后，直接决定观测展示。方案 §7.2 只写了改 `ChatModelObservationConventionConfig` 内部逻辑，**没有收敛这 6 处调用点**——实施后它们仍是散落的字符串字面量，正是本方案要消灭的「隐性约定」同类物（只是从 Langfuse 换成了调用方标识约定）。

**建议**：抽 `CallerType` 枚举/常量（`phase1/planner/llm-reason/subagent-exec/subagent-compress` 及其展示名），集中定义于观测包；业务类引用枚举而非字面量。同时文档里必须写明一条实施铁律：**能力开关关闭时 `mark()` 调用保留、忽略与否由 Convention/命名策略内部决定**——否则最自然的下意识实现是把「是否打标」的条件放进业务代码，直接违反「埋点方零改动」红线（§2.2）。

#### 13.3.2 【重要遗漏】`ToolGuardGate` 是「观测展示策略泄漏进业务代码」的典型

`guard/ToolGuardGate.java`（业务守卫类）里躺着三样纯观测策略：

- `buildGuardSemantic()`（§119–129）：`{decision}.{toolName}[.{model}][.{args}]` 的 span 名后缀拼接格式；
- `compactArgs()` + `ARGS_MAX_CHARS=40`（§112–145）：为「span 名编码」特制的载荷加工（去引号/空白 → 脱敏 → 限长）；
- 注释「Langfuse 不展示自定义属性，模型名与参数摘要编码进 span 名」（§67、§133）。

按你的口径，这些正是**写在业务代码里的硬编码**——它们是「为了让数据在这一个后端里好看」的行为，属于 §3.1 行为适配层的管辖范围，但 §4.3 的改造表和 §7.2 的改动清单里**没有列 `ToolGuardGate`**。换到 Jaeger 后（`semanticNameEncodingRequired=false`），`AgentTracer.start()` 不再拼后缀，但 `ToolGuardGate` 依然在业务类里为它做全套载荷加工（还因此把 `modelName` 作为构造参数注入守卫类），成本和噪声都白付。

**建议**：把「span 名载荷加工」（`compactArgs`/`buildGuardSemantic`/`ARGS_MAX_CHARS`）整体下沉到命名策略/SpanNameEncoder 侧，`ToolGuardGate` 只传原始语义（decision/toolName/modelName/payload，这些本就是观测数据的组成部分，留在调用侧合理）；带语义做不做编码、怎么编码，由能力驱动。注意边界：**「语义内容」留业务侧（合理），「加工格式」沉策略侧（必须）**，这个区分请写进 §7.2，「是否拼」与「怎么拼」两层都要收敛，不能只收敛一层。

#### 13.3.3 【风险同类，非严格硬编码】`agent.` 前缀出现三处事实源

`AgentSpanSpec.NAMESPACE = "agent."`（模型类）、`ObservabilityTraceFilter.DEFAULT_INCLUDE_PREFIXES` 里的 `"agent."`（观测实现类，按口径不算硬编码）、方案 §4.1 新增的 `capabilities.defaultTracePrefixes` 又要再写一遍 `"agent."`。同一个字符串三分拷贝，将来改命名空间（如迁 `agent.biz.`）三处不同步会静默丢数据。**建议**：`defaultTracePrefixes` 的 `agent.` 项由 `AgentSpanSpec.NAMESPACE` 常量派生（`agent.` 是注册表事实源），至少消除两处字面量重复。

### 13.4 一致性小问题（附赠，非重点）

1. **Fail-Open 边界与现状默认矛盾**：§4.2 说「未识别/**未配置**/缺参数 → 降级 Noop」，§9 S2 又说「`TraceBackend` bean **默认解析为 Langfuse**（行为与现状一致）」。而现状是：未配 `LANGFUSE_BASE_URL` 时 span 照常生成、只是导出失败刷屏（B10）。若「未配置 type」真的降级 Noop，行为与现状不一致，S3 的回归基线对不上。**建议分级明确**：`type` 缺省 → Langfuse（兼容现状）；`type=noop` → 整门面空转；Fail-Open 只覆盖「未知 type / 实现类缺失 / 装配异常」，**不覆盖**「参数缺失」——参数缺失走现状路径（埋点照常、导出告警），由 noop/console 显式关闭。
2. **§6.1 `include-prefixes` 合并语义**：建议写明「backend 能力默认前缀 + 用户追加，用户不可删除 backend 默认项」，避免服务端配置误关导致数据全丢；「仅追加」要落到文档配置注释里。
3. **B2 表格统计**：打标处为 6 处（上文表格），「5 处」建议修正。
