# 规划工具路由设计（紧凑目录 + 一体化 LLM 路由 + 保底）

> 解决：工具全量进规划 prompt 的 token 浪费；方案：规划 prompt 用「工具名 + 短标签」紧凑目录，规划 LLM 一次调用内完成"路由（选工具）+ 规划（定参数）"，识别不出时保底加载全量工具。

> 实施说明：本方案在独立 worktree 实施，不直接动 master。实施前先读本设计文档 + `TaskPlanner.askAiForPlan` 现状 + `Agent任务队列方案.md` 的规划链路上下文。

---

## 一、背景与问题

- 全量工具（当前 7 个）的名字+完整描述被**全量**拼进规划 prompt 文本（唯一接入点 `TaskPlanner.askAiForPlan()`），进 LLM 上下文浪费 token。
- 工具数量增多时 token 线性恶化；描述越长（外置 Langfuse 版）越明显。
- 现状确认：
  - `SubTaskAgent` 执行已按 `plan.tasks` 过滤，`.toolCallbacks(callbacks)` 只传计划内工具的原生 schema —— **执行已是按需**。
  - `AiServiceImpl.doChatWithToolcall()` 的 Phase1 主 agent 直调 `chatModel.stream()` **不带工具**。
  - 全量工具进 LLM **只发生在规划 prompt 文本一处**。

## 二、约束与已否决方案

| 方案 | 结论 | 理由 |
|------|------|------|
| 嵌入向量检索（RAG/Tool Retriever） | **否决** | 太重：要接 embedding 模型、预计算、调阈值，运行时多一跳 |
| 关键字规则路由 | **否决** | 脆弱、需维护；当初就是因此才上 LLM 规划的 |
| 两级：独立路由 LLM 调用 + 规划调用 | **否决** | 每请求多一次 LLM 调用，与省 token 目标相悖 |
| **一体化：规划 prompt 内嵌紧凑目录，一次调用既路由又规划** | **采用** | 省 token、不加调用、路由精确度由 LLM 语义保证 |
| **保底：识别不出 → 全量目录重跑一次** | **采用** | 防轻量路由误判（例："明天的博客阅读量"因"明天/量"误判成天气） |

前置依赖：`GuardedToolCallback` 已有 `getRawToolName()` / `getRawToolDescription()` / 静态 `rawName` / `rawDescription`（读注解定义、**不触发外置 Langfuse 解析**），需补 `getRawInputSchema()`。

## 三、总体设计（组件划分）

| 组件 | 位置 | 职责 | 状态 |
|---|---|---|---|
| `ToolRouter` | `com.hmdp.agent.routing` | 门面：`buildCatalog(compact, cbs, history)` 返回目录文本；`isUncertain(rawPlan)` 检测 `__UNCERTAIN__` 标记 | 新增 |
| `CompactCatalogBuilder` | 同包 | 纯逻辑（可独立单测）：拼 `- 名字: 首句标签（参数：…）`；`OVERRIDES` 表；空描述/超长截断 | 新增 |
| `GuardedToolCallback` | 既有 | 补 `getRawInputSchema()`（注解派生、不触发外置解析）供参数名提取 | 改 |
| `FeatureProperties.ToolRouting` | 既有 | `enabled=true`、`maxTagLength=60`；yml `feature.tool-routing.*` | 改 |
| `TaskPlanner.askAiForPlan` | 既有 | 只做编排：问 router 要目录 → 调规划 LLM → 不确定则全量目录重跑一次 | 简化 |

**TaskPlanner 保持薄**：目录构建、标签、参数名、不确定性判定全部在 router 侧；TaskPlanner 只保留 planVars 组装（completedSummary/failedSummary/userInput/currentResponse）+ LLM 调用（抽成 `plannerCall`）。

### 3.1 askAiForPlan 编排（伪代码）

```java
private String askAiForPlan(String input, String response, Long userId,
                            ToolCallback[] toolCallbacks, TaskReport history) {
    boolean compact = featureProperties.getToolRouting() != null
            && featureProperties.getToolRouting().isEnabled();
    String toolsDesc = toolRouter.buildCatalog(compact, toolCallbacks, history);
    String result = plannerCall(input, response, userId, toolsDesc, history);
    if (compact && toolRouter.isUncertain(result)) {
        log.info("[规划] 路由不确定，改用全量目录重试");
        result = plannerCall(input, response, userId,
                toolRouter.buildCatalog(false, toolCallbacks, history), history);
    }
    return result;
}
```

- `plannerCall` = 现有 `askAiForPlan` 的"render SYSTEM_PLANNER + PLANNER_USER → `chatClient.prompt()...call()` + try/catch 返回 `"[]"` 降级"原样抽出的方法。
- `decompose / validatePlan` **不动**；`validatePlan` 的 `callbackIndex` 保持**全量**（否则子集外工具被误判"工具不存在"）。`__UNCERTAIN__` 在进 `validatePlan` 前由编排层拦截。

## 四、紧凑目录格式与 shortTag 规则

### 4.1 格式

```
- 工具名: 首句标签（参数：city, title）
- queryWeather: 查询某城市的当前天气（温度、晴雨），和「天气怎么样」「冷不冷/热不热」一起使用（参数：city）
```

### 4.2 shortTag 规则（CompactCatalogBuilder）

1. **OVERRIDES 优先**：代码内 `static Map<String,String>`（按 toolName，入代码不入 yml——工具元数据属代码，yml 只放行为开关）。
2. 否则取 `GuardedToolCallback.rawDescription(cb)` **首句**：`desc.split("。", 2)[0]` + `replaceAll("\\s+", "")` 压空白。
3. 空描述 → `（无描述）`。
4. **追加参数名**：从 `GuardedToolCallback.getRawInputSchema(cb)` 的 `properties` 取 key（JSON 解析），拼 `（参数：city, title）`。**必做**——压缩丢参数描述后 LLM 会猜错 key（如 `city` 写成「城市」），validatePlan 不校验 params 会直接运行时失败。
5. 超 `maxTagLength` → 截断加 `…`。
6. 目录构建时跳过 `history.isCompleted(name)` / `history.isFinalFailed(name)`（沿用现有过滤）。

### 4.3 现有工具标签核对（实现后逐条验证）

| 工具 | 分类 | 首句提炼结果 | 需 OVERRIDE？ |
|---|---|---|---|
| queryWeather | 天气 | 查询某城市的当前天气（温度、晴雨）… | 否（含城市/天气/晴雨） |
| queryPublishedBlogs | 博客-读 | 查看/浏览/显示当前用户自己的已发布博客列表，我的博客… | 否（含触发词） |
| queryBlogsByTitle | 博客-搜 | 按标题模糊搜索博客… | 否 |
| publishTestBlog | 博客-写 | 发布一篇测试博客，标题自动设为「测试博客」、内容固定 | **是**——首句缺「发博客/写博客/发布」触发词，需 OVERRIDE 补上 |
| queryTotalBlogs | 统计 | 统计/查看当前系统中的博客总数… | 否 |
| queryTotalUsers | 统计 | 统计/查看当前系统中的注册用户总数… | 否 |
| queryTotalShops | 统计 | 统计/查看当前系统中的店铺总数… | 否 |

`publishTestBlog` 建议 OVERRIDE：`"发布一篇测试博客，用户说「发博客」「写博客」「发布」「发一篇」时使用"`。

### 4.4 按用户输入过滤相关工具（实现增强）

`CompactCatalogBuilder.build(..., userInput)` 传入用户输入时，按内置 `TRIGGER_KEYWORDS`（toolName → 触发词列表，代码内置不入 yml）只列命中触发词的工具，减少 planner 候选数（省 token + 降误选）：

- `userInput` 为空 → 放行全部（不误伤）。
- 未登记在 `TRIGGER_KEYWORDS` 的工具**保守放行**（不过滤，防漏）。
- 所有工具都没匹配上（需求模糊）→ **回退全量紧凑目录**，保证 planner 始终有候选。

新增工具时须在 `TRIGGER_KEYWORDS` 登记触发词（与工具描述首句保持同义词集合）。

## 五、保底机制（识别不出 → 全量目录重跑）

- **触发**：规划 prompt 指示"若无法确定哪个工具匹配用户意图，在计划数组里输出 `{"tool":"__UNCERTAIN__"}`"。
- **检测**：`ToolRouter.isUncertain(rawPlan)` = `rawPlan != null && rawPlan.contains("__UNCERTAIN__")`。常量 `UNCERTAIN_MARKER = "__UNCERTAIN__"`。
- **动作**：命中 → 编排层用**全量目录**（所有工具名字+完整注解描述）重跑一次规划。
- **有界**：每轮最多一次重跑；仍不确定 → 视为空计划（`validatePlan` 返回空 → 保持原 AI 回复，终止该轮）。`MAX_ROUNDS=5` 已有总闸。
- **关闭**：`feature.tool-routing.enabled=false` 或 `getToolRouting()==null` → 直接全量目录，与现状零行为差异（Fail-Open）。

> 局限性：保底只覆盖"识别不出"，**覆盖不了"自信选错"**。防自信选错靠 §6 标签消歧。

## 六、标签消歧（防"自信选错"）

紧凑标签必须保留区分词，避免语义相近工具互抢：

- 天气：城市 / 天气 / 气温 / 晴雨
- 博客读：我的博客 / 标题 / 点赞 / 前 10 条
- 博客写：发布 / 发博客 / 写博客
- 统计：博客总数 / 用户数 / 店铺数

首句规则对现有 7 个描述大部分已满足；实现后逐条核对 §4.3，不满足的用 `OVERRIDES` 校准。

## 七、配置

```yaml
feature:
  tool-routing:
    enabled: true        # 默认开；false 时走全量目录，与现状一致
    max-tag-length: 60   # 紧凑标签最大字符数
```

- `FeatureProperties` 新增嵌套类 `@Data public static class ToolRouting { private boolean enabled = true; private int maxTagLength = 60; }`，字段 `private ToolRouting toolRouting = new ToolRouting();`。
- Spring 宽松绑定：`toolRouting` ↔ `tool-routing`。

## 八、规划 prompt 模板改动（agent.prompt.planner.txt）

保留结构，两处：

1. 「可用工具」下方加一行：
   > 工具仅有名称+简介，先按语义匹配用户意图决定规划哪些；若无法确定匹配哪个工具，在计划数组里输出 `{"tool":"__UNCERTAIN__"}`
2. 参数规则改为：
   > 参数名必须与工具简介括号中标注的参数完全一致
