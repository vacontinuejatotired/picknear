# Agent 模块 — 简历项目亮点

> **用途**: 面试自我介绍用  
> **版本**: v3.2 (2026-07-24)  
> **风格**: 务实工程叙事，非 PPT 包装

---

## 项目职责与难点攻克

**LLM Agent 智能对话模块** — 在 Spring AI + DashScope 基础上，为电商系统接入自然语言交互能力，让 AI 能安全地查询/操作业务数据。

---

**难点 1：AI 调接口不失控** — 聊天场景下，AI 可能生成恶意指令（如"删库"、"批量发帖"）或进入穷举循环。我的做法是在 Agent 执行链上设**两道闸口**：

- **前置闸口（输入阶段）**：Prompt 注入检测以本地规则为主（关键词 + 正则），Redis 仅作为辅助限流；Redis 异常时降级为本地阈值，不阻塞对话主流程，安全规则命中时仍按策略阻断。
- **执行闸口（工具调用阶段）**：Guard 代理层统一包装 ToolCallback，过 4 个 Policy（高危名单、需确认名单、正则匹配、Redis 限流），任一拒绝即拦截；工具方法上的 `@RequiredDataPermission` AOP 切面做数据归属兜底校验。

上线至今未发生工具越权操作。

---

**难点 2：避免工具重复执行与局部故障卡死** — 最初 AI 一次回复内会多次尝试调工具，且某个工具失败后整轮中断。重构后拆为三层：决策层（轻量判断是否需要规划）→ 编排层（AI 拆解任务为 JSON 工具列表，做三层校验：JSON 语法→工具存在→历史状态，生成带依赖的任务队列）→ 执行层（串行调度工具调用或 LLM 聚合）。执行中引入"终结状态"机制，部分工具失败不阻塞全链路，且有 `[Round N]` 阶段日志方便追溯。

---

**难点 3：异步线程丢失登录上下文** — Spring AI 的工具回调在独立线程执行，`ThreadLocal` 拿不到用户信息。解决方案很简单：发起调用时用 `.toolContext(Map.of("userId", userId))` 把用户 ID 显式传进去，工具方法加一个 `ToolContext` 参数接收，不走 `UserHolder`。麻烦在于需要确保团队写的每个新工具都遵守这个约定，不能漏传。

---

**难点 4：工具多了之后 Guard 包装容易遗漏** — 手动注册 + 手动包 Guard 全靠人工记，新人容易漏掉守卫导致安全漏洞。我写了一个 `@TargetTool` 注解，启动时自动扫描带此注解的 Bean，通过 `ToolCallbacks.from()` 批量注册，同时自动用 Guard 包装，让安全守卫成为不可跳过的流程。本质上只是利用了 Spring 的组件扫描机制，不是什么框架设计，但核心收益是**安全不依赖人肉记忆**。
