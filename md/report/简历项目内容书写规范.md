# 简历项目内容书写规范

本文用于统一简历项目经历的事实核对、选点、表达和量化方式，适用于后端、Agent、
前端及其他工程类项目。本文是人读规范，不替代代码、配置、运行行为和测试。

## 1. 目标

1. 从项目事实中选出最有区分度的 3 到 5 个点，不平均用力。
2. 每条同时说明动作和结果或边界，能够自然引出面试追问。
3. 控制篇幅，使项目内容适合一页简历。
4. 禁止把半成品、设计稿和无法追溯的数字写成已落地能力。

## 2. 事实与状态

书写前必须先核对代码、配置、日志、压测和测试。原始简历、设计文档和讲解材料
只能提供候选，不能直接作为事实依据。

| 状态 | 含义 | 简历处理 |
|---|---|---|
| 已实现 | 代码、配置、运行行为或测试可证明 | 可作为独立条目 |
| 半实现 | 主链路只有部分闭环，或存在明确缺口 | 不单独成条，只能作为演进方向 |
| 仅设计 | 只有文档、注释、接口或占位实现 | 不进入简历 |

代码、配置、运行行为和测试冲突时，以实际运行证据为准。

## 3. 选点流程

### 3.1 建立候选池

先列 8 到 12 个候选点。每个候选至少记录：

1. 一句话概述。
2. 对应类、文件或配置。
3. 状态。
4. 可量化数据及出处；没有数据时明确写“无实测”。
5. 是否存在边界、缺陷或未完成部分。

### 3.2 四项评分

每项按 1 到 5 分评分：

| 维度 | 判断标准 |
|---|---|
| 辨识度 | 是否区别于常见 CRUD、技术栈和通用校验器 |
| 技术深度 | 是否包含状态机、一致性、隔离、缓存、并发或关键数据结构 |
| 可验证性 | 是否能从代码、配置、日志、测试或压测复核 |
| 面试抗追问 | 是否能说明边界、失败路径、取舍和反例 |

按总分选出 3 到 5 个点。分数接近时，优先选择能形成完整问题链的点。

### 3.3 淘汰规则

优先淘汰：

1. 技术栈堆砌和无业务问题的通用能力。
2. 单纯“加了一层校验”或“引入一个组件”的描述。
3. 无主线的三层校验、通用安全守卫和重复封装。
4. 只用一次、没有真实接入的业务机制。
5. 设计有说明但代码没有闭环的能力。
6. 面试官追问一次就无法给出实现细节的点。

## 4. 简历中的项目格式

项目首行统一写：

```text
项目名 | 角色 | 规模/量级
```

缺失信息写 `【待补】`，不要猜测。规模可以使用工具数、数据量、模型数、端数和
用例数等可验证口径。

项目正文使用 3 到 5 条 bullet：

```text
- **模块名：**动作，机制或边界；结果。
```

每条控制在 1 到 2 行，全部 bullet 总字数不超过 300 字。模块名应直接说明问题和
范围，不写“核心优化”“技术攻坚”等空标题。

## 5. 表达规则

1. 每条必须有动作，并给出结果、边界或状态变化。
2. 不使用“负责、参与、设计、实现、支持”作为句首。
3. 可以使用“落地、重构、引入、搭建、治理、压缩、隔离、校验、扫描、包装、
   拆分、恢复、缓存、编排”等动作词。
4. 不写原因、行动、结果三段式长句，不把方案说明写成实现小作文。
5. 不写“大幅提升、明显降低、彻底解决、保证稳定”等不可验证措辞。
6. 不使用箭头、流程符号、emoji、装饰性符号、复杂括号和多余缩写。
7. 代码标识符只在能增加技术信息时保留，不连续堆类名。
8. 每条至少留下一个可追问点，例如数据结构、并发、一致性、状态机、缓存、
   隔离、降级、失败补偿、安全或性能边界。
9. 项目简介只保留必要背景，不重复技能栏和项目技术栈。

## 6. 数据使用规则

1. 数字只能来自实测、日志、代码常量、压测记录或测试结果。
2. 优先只给业务效果最直接的两条 bullet 配数字，其他条目不硬凑指标。
3. 没有数据时写 `【待补】` 或定性结果，禁止估算。
4. 使用比例、延迟、QPS 或准确率时，必须能说明样本、环境和计算口径。
5. 代码常量只能证明上限或配置值，不能直接写成业务收益。
6. 历史压测数据必须记录机器、线程数、时长、版本和测试接口。
7. 正式投递前，所有 `【待补】` 必须替换为可验证数据或删除。

## 7. 反例与修正

### 7.1 反例：原因长句

不推荐：

```text
认证拦截器每次请求都查 Redis 校验 Token，压测发现响应耗时约 50ms。
引入 Caffeine 本地缓存，定时从 Redis 同步版本号预加载，拦截器耗时明显降低，
测试环境空接口压测 QPS 从 2800 提升至 5000 左右。
```

问题：

1. 原因、行动、结果写成三句长段。
2. “明显降低”没有完整口径。
3. 数字来源和压测条件不足。
4. 一条同时塞入两个缓存机制，后半个机制容易失焦。

### 7.2 修正示例

推荐：

```text
- **认证拦截器缓存：**Token 版本号先查 Caffeine，未命中再查 Redis；版本号定时同步，
  缓存失效异步批量回填。拦截器平均耗时由【待补】降至【待补】，测试环境 QPS 由
  【待补】升至【待补】。
```

保留的追问钩子：

1. 为什么版本号适合本地缓存？
2. 多实例下缓存一致性如何保证？
3. 定时同步失败后的降级路径是什么？
4. 异步回填如何防止旧值覆盖新值？
5. 耗时和 QPS 的测试条件是什么？

## 9. 可复用提示词

```text
你是资深【目标岗位】面试官兼简历顾问。根据我提供的项目原始描述和事实证据，
把项目内容压缩成一页简历中的项目经历。只输出成稿，不展示分析过程。

输入：
目标岗位：【填写】
项目名称：【填写】
原始描述：【粘贴】
事实源：【填写代码、配置、日志、压测、测试或线上记录】
篇幅限制：3 到 5 条 bullet，每条 1 到 2 行，总字数不超过 300 字。

内部选点流程：
1. 先穷举 8 到 12 个候选点，逐项核对事实并标记已实现、半实现或仅设计。
2. 按辨识度、技术深度、可验证性、面试抗追问四项评分。
3. 只选 3 到 5 个最强点。
4. 半实现和仅设计不能单独成条。
5. 淘汰技术栈堆砌、通用安全校验、无主线校验器和普通 CRUD。

事实规则：
1. 代码、配置、运行行为和测试优先于文档。
2. 数字只能来自实测、日志、代码常量、压测或测试结果。
3. 无数据写【待补】或定性结果，禁止估算。
4. 优先只给业务效果最直接的两条 bullet 配数字。

文风规则：
1. 首行格式为“项目名 | 角色 | 规模/量级”。
2. bullet 格式为“- **模块名：**动作，机制或边界；结果”。
3. 每条 1 到 2 行，不写原因、行动、结果长句。
4. 不以负责、参与、设计、实现、支持开头。
5. 不使用箭头、流程符号、emoji、装饰性符号和多余缩写。
6. 每条至少包含一个可追问的技术机制、边界或一致性决策。

输出格式：
项目名 | 角色 | 规模/量级

- **模块名：**动作，机制或边界；结果。
- **模块名：**动作，机制或边界；结果。
- **模块名：**动作，机制或边界；结果。
- **模块名：**动作，机制或边界；结果。

面试追问预埋点

1. 【问题】
2. 【问题】
3. 【问题】
4. 【问题】
5. 【问题】

输出前内部检查：
1. 一页能否放下？
2. 每条是否有动作和结果或边界？
3. 是否出现未证实数字？
4. 是否混入半实现或仅设计能力？
5. 是否删除了通用件和空话？
6. 每条是否都能引出有效追问？
```

## 10. 提交前检查

1. 项目名、角色和规模口径是否准确。
2. 是否只有 3 到 5 条 bullet。
3. 每条是否包含动作和结果或边界。
4. 是否只有最合适的两条 bullet 使用量化指标。
5. 数字是否全部可追溯。
6. 是否删除半实现、仅设计和通用技术堆砌。
7. 是否保留足够的面试追问钩子。
8. 是否删除箭头、emoji 和装饰性符号。
9. 是否适合一页简历的版面。
