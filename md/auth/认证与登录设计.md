# 认证与登录设计

## 1. API

`AuthController` 对外仍使用 `/user/**`，避免破坏已有前端契约。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/user/code` | POST | 发送验证码 |
| `/user/login` | POST | 验证码登录或密码登录 |
| `/user/logout` | POST | 吊销 Token 并清除 Cookie |
| `/user/password` | PUT | 登录态修改密码 |
| `/user/password/reset` | PUT | 验证码重置密码 |

## 2. 登录策略

`LoginStrategyRegistry` 收集所有 `LoginStrategy`，按表单内容路由：

| 策略 | 条件 | 行为 |
|---|---|---|
| `CodeLoginStrategy` | `password == null` | 原子消费验证码，不存在则自动注册 |
| `PasswordLoginStrategy` | `password != null` | 密码校验、失败计数和账户锁定 |

没有策略命中时拒绝登录。

## 3. 验证码

`VerifyCodeService`：

1. 校验手机号；
2. 使用 `login:code:freq:{phone}` 做 60 秒发送频率限制；
3. 生成 6 位数字验证码；
4. 存入 Redis，默认 TTL 由 `LOGIN_CODE_TTL` 控制；
5. 登录时通过 `ConsumeVerifyCode.lua` 执行 GET + DEL 原子消费。

验证码消费成功后立即删除，不能重复使用。

DEV 环境当前会把验证码放入响应体用于调试，生产环境不应保留该行为。

当前代码实际由 `VerifyCodeService.sendCode()` 无条件回显验证码，未按 profile 分支；
项目仅在内网测试范围运行。若后续暴露到公网，必须同时关闭回显并调整
[API 接口文档](../ops/API接口文档.md) 的契约说明。

## 4. 双 Token 生成

`TokenService.generateTokenPair()`：

1. 通过 `RedisIdWorker.nextVersion(userId)` 生成新版本；
2. 生成带 `userId + version` 的 Access Token；
3. 生成随机 Refresh Token；
4. 通过 `LoginSetToken.lua` 原子写入 4 个 Redis key。

| key | 内容 |
|---|---|
| `login:token:access:{userId}` | Access Token |
| `login:token:refresh:{userId}` | Refresh Token |
| `login:valid:version:{userId}` | 当前有效版本 |
| `login:current:version:{userId}` | 新登录版本视图 |

登录会 bump version，使旧会话失效。

## 5. Access Token 校验

`TokenService.validateAccessToken()`：

```text
JWT 签名与过期校验
  -> Caffeine 快速版本拒绝
  -> Redis validVersion 最终校验
  -> 判断是否临期
```

校验结果包括：

- `valid`
- `userId`
- `version`
- `needsRefresh`

Access Token 过期时仍解析 Claims，进入带锁刷新流程。

## 6. Refresh Token 刷新

### 6.1 读取顺序

`RefreshTokenInterceptor` 先读：

```text
Refresh-Token 请求头
  -> httpOnly refresh_token Cookie
```

双通道用于兼容跨 host 和浏览器 Cookie 丢失场景。

### 6.2 分布式锁

刷新锁：

```text
lock:refresh:{userId}
```

默认持有 3 秒。并发请求未抢到锁时返回 `SKIPPED`，不覆盖其它请求刚写入的新 Token。

### 6.3 Lua 原子刷新

`RefreshExpiredToken.lua` 同时校验并更新：

- Refresh Token；
- Access Token；
- validVersion；
- currentVersion。

刷新不会 bump version，仍使用旧版本，只做滑动续期。

### 6.4 并发自愈

Refresh Token 不匹配时，`ReadCurrentToken.lua` 读取当前凭证。

仅当当前有效版本等于旧版本时，才把当前 Token 返回给并发请求，避免把新登录会话的凭证泄露给旧会话。

### 6.5 返回头

刷新成功后：

```http
X-Token-Refresh: ok
authorization: Bearer <new-access-token>
Refresh-Token: <new-refresh-token>
Set-Cookie: refresh_token=...
```

刷新失败：

```http
X-Auth-Reason: superseded | no-session
```

- `superseded`：账号已在其他设备登录；
- `no-session`：登录已过期或会话不存在。

锁被占用时：

```http
X-Token-Refresh: skipped
```

## 7. 拦截器

### 7.1 RefreshTokenInterceptor

负责：

1. 检查 `authorization`；
2. 调用 `TokenService.validateAccessToken()`；
3. 将用户信息写入 `UserHolder`；
4. 临期或过期时执行刷新；
5. 写回响应头和 Cookie；
6. `afterCompletion` 清理 `UserHolder`。

### 7.2 LoginInterceptor

仅校验 `UserHolder` 是否存在用户。

公开接口不经过登录拦截；需要登录的接口在 `RefreshTokenInterceptor` 后执行。

## 8. 用户上下文

`SessionContextService.saveUserToContext()`：

```text
userId 写入 UserHolder
  -> Caffeine 查询 userId + nickName + icon
  -> 信息不完整时查询 DB 回填
  -> UserDTO 写入 UserHolder
```

缓存或 DB 异常按未登录处理。

## 9. 密码登录

### 9.1 新用户

手机号不存在且提供密码时，自动创建带 BCrypt 密码的账号。

### 9.2 已有用户

1. 检查账户锁定；
2. `PasswordEncoder.matches()` 校验；
3. 失败累计 `login:fail:count:{phone}`；
4. 连续失败达到阈值后设置 `login:lock:{phone}`；
5. 成功后删除失败计数。

旧 MD5 + Salt 密码验证成功后自动升级为 BCrypt。

密码规则：

```text
至少 8 位，包含大写字母、小写字母和数字
```

当前锁定只按手机号维度执行，尚没有 IP 级或代理来源级登录限频。

## 10. 改密与重置

### 10.1 修改密码

`PasswordService.changePassword()`：

1. 校验旧密码；
2. 校验新密码强度；
3. BCrypt 更新；
4. bump version 并重新生成双 Token；
5. 旧 Token 自动失效。

### 10.2 重置密码

`PasswordService.resetPassword()`：

1. 原子消费验证码；
2. 校验密码强度；
3. 更新密码；
4. 不直接返回 Token。

## 11. 登出

`SessionContextService.revokeTokens()` 删除：

- Access Token；
- Refresh Token；
- validVersion；
- currentVersion；

同时清理用户信息和版本 Caffeine 缓存。

Controller 清除客户端 refresh Cookie，并通过空 `authorization` 响应头通知前端清理本地 Token。

## 12. 不变量

1. 登录会 bump version，刷新不会。
2. Access Token 必须同时通过 JWT 和版本校验。
3. 验证码必须原子消费。
4. Refresh Token 不能只存 localStorage，必须同时写 httpOnly Cookie。
5. 401 必须携带可区分的 `X-Auth-Reason`。
6. 修改密码必须 bump version，使旧 Token 失效。
